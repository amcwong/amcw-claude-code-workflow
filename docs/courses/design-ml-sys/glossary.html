Glossary

Glossary

Cumulative, beginner-facing, grouped by the book chapter where each term is introduced (not A–Z). Each entry is one sentence plus a link to the section that introduces it. A later chapter may add a stricter sense of a term, but the original entry stays.

Chapter 1

  • ML system. The whole production setup around a model: requirements, interfaces, data stack, the logic for developing, deploying, monitoring, and updating models, and the infrastructure that runs it. See Chapter 1, What an ML system is.
  • MLOps. The tools and best practices for bringing ML into production (deploying, monitoring, maintaining). See Chapter 1, What an ML system is.
  • ML systems design. A system approach to MLOps that treats all components and stakeholders as a whole so they meet the stated objectives. See Chapter 1, What an ML system is.
  • Five-part test. ML learns complex patterns from existing data to make predictions on unseen data; a problem should satisfy each part before ML is used. See Chapter 1, The five-part test.
  • Zero-shot learning. Predicting on a task with no training data for that task, by relying on training for related tasks. See Chapter 1, The five-part test.
  • i.i.d. assumption. Training and future data are drawn independently from the same distribution; ML’s usefulness on unseen data depends on it roughly holding. See Chapter 1, The five-part test.
  • Distribution shift. The serving data distribution differs from the training distribution. See Chapter 1, The five-part test; monitored in Chapter 8.
  • Concept drift. The pattern relating inputs to outputs changes over time, so fixed rules or models go stale. See Chapter 1, When ML shines.
  • Ensembling. Combining several learning algorithms to beat any one of them; common in competitions, less common in production because of latency and interpretability costs. See Chapter 1, Stakeholders and requirements.
  • Latency. Time from sending a query to receiving its result (this book uses it to mean response time). See Chapter 1, Computational priorities.
  • Throughput. Number of queries processed per unit time; with sequential batches, batch size divided by time per batch. See Chapter 1, Latency and throughput under batching.
  • Percentile (p50, p90, p99). The value below which roughly that percentage of measurements fall; p50 is the median. Used for latency targets; tail percentiles need many samples to be stable. See Chapter 1, Latency is a distribution.
  • Algorithmic bias. Systematic model error that disadvantages a group, often inherited from training data and amplified by scale. See Chapter 1, Fairness.
  • Interpretability. How far people can understand why a model produced an output; needed for user trust, bias detection, and debugging. See Chapter 1, Interpretability.
  • Data poisoning. Planting training examples to manipulate a model’s behaviour. See Chapter 1, ML systems versus traditional software.

Chapter 2

  • Business objective vs ML objective. What the organization wants (revenue, retention) versus a measurable property of the model (accuracy, latency); the second matters only through the first. See Chapter 2, Business and ML objectives.
  • Take-rate. Netflix’s recommender metric: quality plays divided by recommendations seen, used as a bridge to business metrics. See Chapter 2, Business and ML objectives.
  • Reliability. Keeping the correct function at the desired performance despite faults; ML systems can fail silently. See Chapter 2, Reliability.
  • Scalability. Reasonable ways to handle growth in model complexity, traffic, and model count, through resource scaling and artifact management. See Chapter 2, Scalability.
  • Autoscaling. Automatically adding or removing machines as usage changes. See Chapter 2, Scalability.
  • Maintainability. Structuring work so mixed teams can use their own tools, with documented, versioned, reproducible code, data, and models. See Chapter 2, Maintainability.
  • Adaptability. Finding where to improve and updating without service interruption, to keep up with shifting data and requirements. See Chapter 2, Adaptability.
  • ML problem. A problem defined by its inputs, outputs, and objective function. See Chapter 2, Framing ML problems.
  • Classification vs regression. Predicting a category versus a continuous value; each can be reframed as the other (bucketing, or a probability plus a threshold). See Chapter 2, Classification versus regression.
  • Decision threshold. The cutoff that turns a predicted score or probability into a class; it need not be 0.5. See Chapter 2, Classification versus regression.
  • High cardinality. A classification task with a very large number of classes, which makes collecting enough examples of rare classes hard. See Chapter 2, Binary versus multiclass classification.
  • Hierarchical classification. Classifying first into a coarse group, then into a subgroup with a second classifier. See Chapter 2, Binary versus multiclass classification.
  • Multilabel classification. Each example can belong to several classes at once, encoded as a multi-hot vector. See Chapter 2, Multiclass versus multilabel classification.
  • Objective (loss) function. The function training minimizes, comparing predictions with labels; distinct from a business or ML objective. See Chapter 2, Objective functions.
  • Cross-entropy. -\sum_i p_i \log q_i; with a one-hot label, minus the log of the probability on the true class. Log loss is the binary case. See Chapter 2, Objective functions.
  • Decoupling objectives. Training one model per objective and combining their scores, so trade-offs can be retuned without retraining. See Chapter 2, Decoupling objectives.
