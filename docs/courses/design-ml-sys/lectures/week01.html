Chapter 1: Overview of Machine Learning Systems

Chapter 1: Overview of Machine Learning Systems

Overview. This chapter asks two questions before any model is trained: when is machine learning (ML) the right tool at all, and what changes when a model leaves the notebook and runs in production? The answers set up the rest of the book. A production ML system is mostly not the algorithm. It is the requirements, data, infrastructure, and the logic for deploying, monitoring, and updating models. Most of the chapter contrasts ML in research with ML in production along five axes (stakeholders, computational priority, data, fairness, interpretability), then contrasts ML systems with traditional software.

What an ML system is

When people hear “machine learning system,” they usually picture the algorithm: logistic regression, a gradient-boosted tree, a neural network. What else has to exist before that algorithm is useful to anyone?

Definition. An ML system is the whole production setup around a model: the business requirements that motivated it, the interface where users and developers interact with it, the data stack, the logic for developing, evaluating, deploying, monitoring, and updating models, and the infrastructure that delivers that logic.

The book is organized around this picture. Figure 1 redraws the book’s Figure 1-1 and marks which chapter covers each part.

Two terms come up immediately and are easy to blur in an interview.

Definition. MLOps is a set of tools and best practices for bringing ML into production: deploying, monitoring, and maintaining models. The “Ops” comes from DevOps (development and operations); to operationalize something is to bring it into production.

ML systems design takes a system approach to MLOps. It considers the ML system as a whole, so that all the components and their stakeholders work together to meet the stated objectives and requirements.

So MLOps names the practices and tooling, and systems design is the discipline of fitting all the pieces (and people) together. The book deliberately covers no algorithm in detail. Algorithms go out of date quickly, while the framework for choosing and running one should survive them.

When to use machine learning

ML can solve many problems, but even for problems it can solve, it may not be the best solution. Before starting a project, ask whether ML is necessary and whether it is cost-effective. (The book notes it never asks whether ML is sufficient, because the answer is always no: ML is always one part of a larger system.)

The five-part test

The book frames what ML does in one sentence and then examines each part.

Definition. Machine learning is an approach to (1) learn (2) complex patterns from (3) existing data and use these patterns to make (4) predictions on (5) unseen data.

Each phrase is a condition a problem must satisfy.

  1. Learn: the system can learn. A relational database is not an ML system. You can state a relationship between two columns, but the database cannot discover one. In supervised learning, the system learns from input–output pairs. The book’s running example: learn to predict an Airbnb listing’s rental price from its characteristics (square footage, rooms, neighborhood, amenities, rating), given a dataset of listings and their prices.

  2. Complex patterns: there are patterns, and they are complex. There is no pattern to learn in the outcome of a fair die. (The book separates patterns from distributions: we know the distribution of a fair die exactly, but nothing about how each outcome is generated is learnable.) If the pattern is simple, skip ML. Mapping an Airbnb listing’s zip code to its state needs a lookup table, not a model. Mapping a listing’s characteristics to its price is complex enough that hand-specifying it is impractical, which is where ML fits. What is complex for machines differs from what is complex for humans: raising a number to the power of 10 is easy for a machine, while spotting a cat in a photo used to be hard.

  3. Existing data: data is available, or can be collected. No tax and income records, no tax-prediction model. Two edge cases look like exceptions but are not. In zero-shot learning, a model predicts well on a task it never saw data for, but it was trained on data for related tasks. In continual learning, a model can be deployed untrained and learn from production traffic, at the risk of a poor experience for early users. Without data, some companies “fake it till they make it”: humans make the predictions at first, and the logged results later become training data.

  4. Predictions: the problem is predictive. ML outputs predictions, so it suits problems where many cheap, approximate answers are useful. Many questions can be reframed as “what would the answer be?”, including about the present or past. Compute-heavy processes are a common case: rather than run the exact computation, train a model to approximate its output (the book’s examples are image denoising and screen-space shading in graphics).

  5. Unseen data: unseen data shares patterns with the training data. A model trained on 2008 app-store data will not predict which apps get downloaded on Christmas 2020. Technically, training and unseen data should come from similar distributions. We cannot know the distribution of data we have not seen, so we assume (for instance, that users behave tomorrow roughly as they did today) and check with monitoring.

Definition. Condition 5 is the informal version of the assumption that data are independent and identically distributed (i.i.d.): training examples and future examples are drawn from the same distribution. When that fails in production we call it distribution shift.

Distribution shift is the subject of Chapter 8 (monitoring), and adapting to it is Chapter 9 (continual learning and testing in production).

Figure 2 shows the contrast behind conditions 1 and 2. Traditional software takes inputs plus hand-written patterns and produces outputs. ML takes inputs plus outputs and produces the patterns. This is why Andrej Karpathy called ML “Software 2.0.”

When ML shines

Given how most current algorithms learn, ML works especially well when the problem has four more traits.

  • It is repetitive. Humans learn from a few examples. Most ML algorithms need many, so a pattern that repeats often is easier to learn.
  • Wrong predictions are cheap. No model is right every time. Recommender systems are a large ML use case partly because a bad recommendation costs little: the user just does not click. If a single mistake can be catastrophic, ML can still make sense when the benefit of correct predictions outweighs the cost of wrong ones on average. The book’s example is self-driving cars, which are worth pursuing if they become statistically safer than human drivers despite the risk of fatal errors.
  • It is at scale. ML needs real up-front investment in data, compute, infrastructure, and people, so it pays off when the model makes many predictions. Some problems that look like one prediction are really many. An election-outcome model predicts once every four years in name, but in practice it updates its prediction hourly as new information arrives. Scale also means more data to train on.
  • The patterns keep changing. Hand-written rules go stale. Spam that today features a foreign prince will tomorrow feature something else. An ML model can be retrained on new data without anyone working out exactly how the data changed (this is the problem concept drift names; Chapters 8 and 9 return to it).

The “wrong predictions are cheap” trait is an expected value argument. Written as a rule of thumb:

P(\text{correct}) \cdot \text{benefit} \;>\; P(\text{wrong}) \cdot \text{cost}

The left side is the average value of being right and the right side is the average cost of being wrong. ML is a reasonable choice when the expected value of acting on its predictions beats the expected cost of its errors, even if individual errors are severe.

When not to use ML

Most current ML algorithms should not be used if any of these hold:

  • It is unethical. (The book’s Chapter 11 has a case study on an automated grader’s biases.)
  • A simpler solution does the job. Chapter 6 makes “start with a non-ML solution” the first phase of model development.
  • It is not cost-effective.

Even when ML cannot solve a whole problem, it may solve a piece of it. If a chatbot cannot answer every customer query, a model can still predict whether a query matches a frequently asked question: if so, show the answer; if not, route the customer to a human. The book also cautions against rejecting a technology only because it is not cost-effective yet, since most advances are incremental and waiting for others to prove it can leave a company years behind.

Machine learning use cases

Consumers meet ML mainly through search and recommendations, predictive typing, photo enhancement, face or fingerprint unlock, machine translation, smart assistants, and home monitoring (such as fall detection for an elderly person living alone). But most ML use cases are in the enterprise, and enterprise requirements differ.

Definition. As a general tendency (with many exceptions), enterprise ML applications have stricter accuracy requirements but are more forgiving of latency than consumer applications.

The book’s reasoning: moving a speech recognizer from 95% to 95.5% accuracy is unnoticeable to most consumers, but a 0.1% efficiency gain in a large company’s resource allocation can be worth millions. Meanwhile, a one-second delay can send a consumer to another app, while an enterprise user will usually wait.

The enterprise uses the chapter names, grouped by what they do:

Use case What the model predicts
Fraud detection Whether a transaction is fraudulent, learned from past fraud (anomaly detection); one of the oldest enterprise uses
Price optimization The price for a time period that maximizes an objective (margin, revenue, growth); suits many transactions with fluctuating demand, such as ads, flights, ride-sharing
Demand forecasting Customer demand, for budgeting, inventory, and staffing (understock loses sales; overstock spoils)
Customer acquisition Which prospects to target, which ads to show, when to offer discounts
Churn prediction When a customer (or employee) is about to leave (customer attrition); retaining a customer is estimated to cost 5 to 25 times less than acquiring a new one
Support ticket classification Which department a ticket should go to, shortening response time
Brand monitoring Mentions of the brand and their sentiment (sentiment analysis)

Health care is singled out. There are systems that detect skin cancer and diagnose diabetes, but because of strict accuracy and privacy requirements they are usually delivered through a health-care provider or used to assist a clinician’s diagnosis, rather than sold directly to consumers.

ML in research versus in production

Most people with ML expertise learned it in academia: courses, research, papers. The book’s claim is that production ML differs from research ML in at least five ways, summarized in its Table 1-1.

Stakeholders and requirements

A research or leaderboard project usually has one objective: beat the state of the art on a benchmark. A production project has many stakeholders, each with their own, often conflicting, requirements.

The book’s running example is a restaurant-recommendation app that earns a 10% service fee on each order, so expensive orders earn more.

  • ML engineers want to recommend the restaurants users are most likely to order from, and believe a more complex model with more data will do it.
  • Sales wants to recommend expensive restaurants, because they bring in larger fees.
  • Product has seen that every increase in latency loses orders, and wants recommendations returned in under 100 milliseconds.
  • The ML platform team is being paged at night over scaling problems, and wants to pause model updates to fix the platform.
  • The manager wants to maximize margin (and one way to do that might be to cut the ML team).

“Recommend what users will most likely click” and “recommend what earns the most” are different objectives. Chapter 2 resolves this by decoupling objectives: train one model per objective and combine their predictions. Suppose model A optimizes clicks and model B optimizes revenue, and neither meets the 100 ms requirement. Which do we deploy? It depends on how strict each requirement is. If 100 ms is a must-have (say, the company found 10% of users close the app beyond that), neither model works. If it is a nice-to-have, either might. Part of the ML engineer’s job is finding out which requirements are hard constraints.

This mismatch is one reason successful research often does not ship. Ensemble learning is the book’s example.

Definition. Ensembling combines multiple learning algorithms to obtain better predictive performance than any of the constituent algorithms could alone.

Ensembles win competitions, including the Netflix Prize, but they are not widely used in production. The small accuracy gain usually costs slower predictions and results that are harder to interpret. (Chapter 6 covers ensembles properly.) Whether a small gain is worth that cost depends on the task. A 0.2% improvement in click-through rate for an e-commerce recommender can be worth millions in revenue. For many other tasks users would not notice a small gain, so a complex model has to beat a simple one by a wide margin to justify itself.

Note

Criticism of ML leaderboards. The book summarizes three objections to leaderboards like Kaggle, ImageNet, and GLUE:

  1. The hard steps of building an ML system (framing the problem, collecting and labeling data) are already done for you.
  2. When many teams evaluate against the same held-out test set, one model can come out on top by chance. This is a multiple comparisons problem.
  3. Ethayarajh and Jurafsky (EMNLP 2020) argue that benchmarks reward accuracy at the expense of qualities practitioners value, such as compactness, fairness, and energy efficiency.

Computational priorities

People who have not deployed a model tend to focus on model development and neglect deployment and maintenance. During development we train many models, each over many passes through the training data, and evaluate each once on a smaller validation set, so training is the bottleneck. Once deployed, the model’s job is to make predictions, so inference is the bottleneck. Research prioritizes fast training; production prioritizes fast inference.

A corollary is that research cares about throughput and production cares about latency.

Definition. Latency is the time from receiving a query to returning its result. Throughput is how many queries are processed in a given period of time.

The book flags a terminology clash. Kleppmann’s Designing Data-Intensive Applications separates response time (what the client sees, including network and queueing delays) from latency (only the time a request waits to be handled). The book, following ML usage, uses “latency” to mean the full response time: from when a request is sent to when the response arrives. In an interview it is worth saying which one you mean.

Latency and throughput under batching

If a system handles one query at a time, the two quantities are tied: higher latency means lower throughput. At 10 ms per query, throughput is 100 queries per second; at 100 ms, it is 10. Most modern systems instead process queries in batches, often concurrently, and then higher latency can come with higher throughput. When batches run one after another,

\text{throughput} = \frac{\text{batch size}}{\text{time per batch}}

so a larger batch can raise throughput even if each batch takes longer.

Note

Worked example (the book’s numbers).

  • One query at a time, 10 ms each: latency 10 ms, throughput 1 / 0.010\,\text{s} = 100 queries/s.
  • Batches of 10, each taking 10 ms: latency is still 10 ms, but throughput is 10 / 0.010\,\text{s} = 1{,}000 queries/s.
  • Batches of 50, each taking 20 ms: latency rises to 20 ms, and throughput rises to 50 / 0.020\,\text{s} = 2{,}500 queries/s.

In the last line both latency and throughput went up compared with the first.

These numbers leave out one cost. For online queries, a batch has to fill before it runs, so each query also waits for the others to arrive, which adds latency the worked example does not count. Research happily trades latency for throughput through aggressive batching. Production often cannot: lowering latency may mean running fewer queries at a time on the same hardware, which underuses that hardware and raises the cost per query.

Latency matters commercially. The book cites a 2017 Akamai study finding that a 100 ms delay can cut conversion rates by 7%, and Booking.com finding that roughly 30% more latency cost about 0.5% in conversions.

Latency is a distribution

It is tempting to summarize latency as one number, the mean over a time window. That number can mislead, because latency is a distribution and the mean is pulled by outliers.

Definition. The q-th percentile (written pq) of a set of measurements is a value below which roughly q% of the measurements fall. p50 is the median: half of requests are faster, half slower. Latency targets usually use high percentiles: p90, p95, p99 (sometimes p99.9).

Note

Worked example (the book’s 10 requests). Latencies in ms: 100, 102, 100, 100, 99, 104, 110, 90, 3,000, 95.

  1. Mean. The sum is 3,900 ms, so the mean is 3{,}900 / 10 = 390 ms. Nine of ten requests took about 100 ms, so 390 ms makes the system look much slower than it usually is.
  2. Sort. 90, 95, 99, 100, 100, 100, 102, 104, 110, 3,000.
  3. Median (p50). The middle two values are 100 and 100, so p50 = 100 ms, which describes the typical request.
  4. The outlier. The 3,000 ms request is an outlier, perhaps a network error, and is worth investigating on its own.

The book says the p90 of these ten requests is 3,000 ms. That depends on which percentile definition you use, and with only ten samples the definitions disagree widely:

  • Nearest rank (take the \lceil 0.9 \times 10 \rceil = 9th sorted value): p90 = 110 ms.
  • Linear interpolation (NumPy’s default; position 0.9 \times (10-1) = 8.1 in 0-indexed order, so one tenth of the way from 110 to 3,000): p90 = 110 + 0.1 \times 2{,}890 = 399 ms.
  • Round up to the next sample (NumPy’s method="higher"): p90 = 3,000 ms, the book’s figure.

The practical lesson is that a tail percentile computed from a handful of requests is unstable. A real p99 needs enough traffic that 1% of it is many requests.

High percentiles matter because the slowest requests can come from the most important users. At Amazon, the customers with the slowest requests are often those with the most data on their accounts, because they have made the most purchases. So performance requirements are commonly written as tail percentiles, for example “p90 (or p99.9) latency must stay below some threshold.”

Data

Research datasets are clean, well formatted, and static so the community can benchmark against them. Many people have used them, their quirks are known, and preprocessing scripts are often public.

Production data, if it exists at all, is messier:

  • noisy, possibly unstructured, and constantly shifting;
  • likely biased, in ways you probably do not know;
  • labels, if any, may be sparse, imbalanced, or wrong, and changing business requirements can force relabeling;
  • user data brings privacy and regulatory obligations.

Research mostly uses historical data that already sits somewhere. Production also consumes data generated continuously by users, systems, and third parties. The book illustrates this with a graphic adapted from Andrej Karpathy (its Figure 1-5): during his PhD most of his time went to models and little to data, while at Tesla the proportions reversed.

Fairness

In research a model is not yet used on people, so fairness is easy to postpone: “get state of the art first, worry about fairness in production.” By production it is too late. Accuracy and latency have public benchmarks to beat; fairness, as of the book’s writing, has no equivalent state of the art.

The examples are concrete: a loan rejected because the model leans on zip code, which encodes socioeconomic background; a résumé ranked lower because of the spelling of a name; a mortgage rate tied to credit scores that favor the wealthy. The book quotes a 2019 Berkeley study finding that lenders rejected about 1.3 million creditworthy Black and Latino applicants between 2008 and 2015.

Definition. Algorithmic bias is systematic error in a model’s outputs that disadvantages some group. In the book’s phrasing, ML algorithms “don’t predict the future, but encode the past,” so they reproduce the biases in their training data, and at scale.

Scale is what makes this worse than individual human bias. A human makes sweeping judgments about a few people at a time; a model can make them about millions in seconds. And aggregate metrics hide it. Errors on a minority group barely move overall performance: a model that is correct on 98% of a population can be badly wrong on the other 2%, and if fixing that 2% would cost several times more, some companies choose not to. This is the same arithmetic as a rare-positive classification problem, where a high overall accuracy says little about the small class. Chapter 11 covers fairness and responsible AI in depth.

Interpretability

Geoffrey Hinton posed this question in 2020: if you had cancer, would you choose a black-box AI surgeon with a 90% cure rate that cannot explain how it works, or a human surgeon with an 80% cure rate? When the book’s author asked 30 technology executives, they split about evenly.

Definition. A model is interpretable (or explainable; see explainable artificial intelligence) to the extent that people can understand why it produced a given output.

Research is still scored mainly on performance, so researchers have little incentive to work on interpretability. In industry it is usually a requirement, for two reasons:

  1. For users (business leaders and end users): to understand why a decision was made, so they can trust the model and detect the biases described above.
  2. For developers: to debug and improve the model.

In some countries and for some uses there is also a legal right to explanation of an algorithm’s output. This is the clinical setting of the Hinton question: a clinician deciding whether to act on a model’s flag needs a reason, not only a score. The book does not cover specific explanation methods in this chapter.

The book closes the comparison with a short discussion: knowing only the academic side of ML is fine, but most companies cannot fund pure research without short-term applications, so most ML jobs are, and will be, in putting ML into production.

ML systems versus traditional software

ML is part of software engineering, and software engineering has decades of production practice. Why not just apply those practices? Partly we should: production ML would be better if ML practitioners were better software engineers, and many standard tools apply. But some challenges are specific to ML.

Code and data are entangled. Software engineering separates concerns and keeps code and data apart (separation of concerns). An ML system is part code, part data, and part artifacts built from both. Because the best data tends to win, companies put more effort into data than into algorithms, and because data changes quickly, ML systems need faster development and deployment cycles.

Data must be tested and versioned too. In ordinary software we test and version code. In ML we also have to test and version data, which is harder. How do you version a large dataset? How do you tell whether a sample helps or hurts?

Not all samples are equally valuable. The book’s example: a model already trained on one million scans of normal lungs and one thousand scans of cancerous lungs gains far more from another cancerous scan than another normal one. This is the class-imbalance problem seen from the data side, and Chapter 4 (training data) returns to it. Accepting all incoming data indiscriminately can hurt performance and expose the model to data poisoning, where an attacker plants training examples to manipulate the model (a form of adversarial machine learning).

Models are large. As of 2022, models with hundreds of millions or billions of parameters need gigabytes of memory just to load. Getting them into production, especially on edge devices (covered in Chapter 7), is a major engineering task, and they also have to run fast enough to be useful. An autocomplete model that is slower than your typing is useless. The book’s example of progress: in 2018 people called BERT (large BERT: 340 million parameters, 1.35 GB) too big and slow to be practical; two years later it and its variants were used in almost every English search on Google.

Monitoring and debugging are harder. As models grow more complex and less transparent, it is harder to see what went wrong, or to be alerted quickly when something does.

Summary

Note

Key takeaways from Chapter 1 (and what an interviewer is usually checking):

  • The algorithm is a small part of the system. Requirements, data, infrastructure, and deployment, monitoring, and update logic are most of the work. MLOps is the tooling and practice; ML systems design is fitting the whole thing together.
  • Justify ML before using it. Check the five-part test (learn, complex patterns, existing data, predictive, unseen data resembles training data) and the four traits (repetitive, cheap errors on average, at scale, changing patterns). Name the alternatives: a lookup table, a rule, or a non-ML baseline.
  • Production has many stakeholders. Expect conflicting objectives, and separate must-have constraints from nice-to-haves. Ensembles show how a research win can fail production constraints on latency and interpretability.
  • Latency and throughput are different. Batching can raise both. Production usually optimizes latency, and latency should be reported as percentiles (p50, p90, p99), not a mean, with enough samples for the tail to be stable.
  • Production data shifts. Training and serving distributions should match (the i.i.d. assumption), and in production they often drift.
  • Fairness and interpretability are requirements in production. Aggregate accuracy can hide failure on a small subgroup; users need explanations to trust a model, and developers need them to debug it.
  • ML differs from traditional software because data is part of the system: it needs testing and versioning, samples differ in value, and it can be poisoned.

Quick self-check

If you can explain to an interviewer, using only “five-part test,” “latency versus throughput,” and “research versus production,” why a team might ship a simple model instead of a 0.5%-better ensemble, you have understood the core of Chapter 1.
