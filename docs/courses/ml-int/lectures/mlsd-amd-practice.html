ML system design practice: AMD Projects 17, 18, and 19

ML system design practice: AMD Projects 17, 18, and 19

Overview. These 50 problems drill the ideas in Machine Learning System Design Interview (Aminian and Xu), one part per book chapter, so that every chapter is covered. Each question is set inside one of three AMD MScAC internship projects, named in the line under its heading:

  • Project 17, Intelligent Overclocking (AIO). Use telemetry from real systems and workloads to predict GPU operating parameters (frequency limits, power limits, voltage settings) that raise performance while meeting stability targets, and that generalize across hardware generations and workloads.
  • Project 18, context and intent pre-check. Before a coding agent runs, discover the intent and context behind a ticket, detect missing or conflicting information, and decide whether to pass the ticket to the agent or hold it for clarification.
  • Project 19, traceable workflows and failure feedback. Turn feature requirements into structured agent workflows with traces that link requirements to steps, code changes, and tests, then attribute failures to the stage that caused them and repair them with targeted feedback instead of blind retries.

Try each stem before opening the worked solution. Every dataset, number, and system detail in the stems is invented for practice. The solutions explain the book’s ideas in our own words and then apply them to the project.

Chapter 1: The framework

The book answers every design question with the same seven steps: clarify requirements, frame the problem as an ML task, prepare data, develop the model, evaluate, deploy and serve, then monitor. Problems 1 to 11 walk through those steps once.

Problem 1: Clarifying a vague design prompt

Inspired by Project 18 (context and intent pre-check). Book: Chapter 1, Clarifying Requirements.

An interviewer says only: “Design a system that checks tickets before a coding agent works on them.” List the clarifying questions you would ask in the first five minutes, grouped by category, and say how the answers would change the design.

TipWorked solution

Design prompts are deliberately vague. The first step is to agree on scope by asking questions in a few fixed categories, then writing the agreed requirements down so both sides work from the same list.

Category Questions for this prompt How an answer changes the design
Business objective Is the goal to save agent compute, to save reviewer time, or to raise the quality of fixes that get merged? Sets the ML objective and the online metric (Problem 27).
Features to support Does a held ticket go back to its author with a list of what is missing? Can engineers override a hold? An explanation requirement rules out a single yes/no model (Problem 25). Overrides become labels.
Data Do we have historical tickets with known outcomes (fixed, reverted, abandoned)? Are any labelled by experts for sufficiency? Decides between natural labels and hand labels (Problem 6).
Constraints Must it run inside the existing agent harness? Can it call an LLM, or must it be a cheap classifier? Are some repositories private? Limits model size and cost per ticket, and adds permission filtering (Problem 15).
Scale How many tickets per day? How many repositories, files, and documents must the context search cover? Decides whether exact search is affordable or approximate search is needed.
Performance Must the decision arrive before the agent starts, within seconds? Is it worse to hold a good ticket or to pass a bad one? Sets the latency budget and where the decision threshold sits (Problem 26).

The book also says to raise privacy and ethics where relevant. Here that means the tickets and the code they point at may be confidential, so the context search must respect access controls.

A strong answer ends by restating the agreed problem in two or three sentences, for example: “Given a ticket and its repository, output pass or hold, plus a list of missing items, within a few seconds. Labels come from historical outcomes, plus a small expert-labelled set for evaluation.”

Answer. Ask about the business objective, the features to support, the data, the constraints, the scale, and the performance needs (latency, and which error is worse). Then write the agreed scope down. Each answer fixes a later design choice: objective and metrics, model type, labelling, and the decision threshold.

Problem 2: From “faster but still stable” to an ML task

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 1, Frame the Problem as an ML Task.

The business goal is: “Give users more GPU performance through automatic tuning, without making their systems less stable.” Turn this into one or more ML objectives. For each model, give its inputs and outputs and its ML category. Where would workload classification fit?

TipWorked solution

“More performance without less stability” is a business goal, not something we can train on. The book’s recipe has three steps: define a measurable ML objective, specify each model’s inputs and outputs, and choose the ML category.

The ML categories. The book’s tree of categories starts with three kinds of learning:

  • Supervised learning learns from examples paired with correct answers (labels).
  • Unsupervised learning finds structure in data with no labels, for example clustering.
  • Reinforcement learning learns by trial and error, acting in an environment and receiving rewards.

Supervised learning then splits into classification (predict a discrete class: binary for two classes, multiclass for more) and regression (predict a number, so we must state its output range).

Here, validation runs give labelled examples: a configuration was tried, and we measured its speed-up and whether it crashed. So supervised learning fits. Reinforcement learning would explore configurations on real machines, and every “trial” that goes wrong is a crashed system. Unsupervised learning could group similar workloads, but it cannot predict a gain or a risk on its own.

One workable framing uses two supervised models and a decision rule.

Model Input Output ML category
Performance model GPU features, workload features, a candidate configuration (frequency limit, power limit, voltage offset) predicted performance gain, such as % change in frame rate regression
Stability model the same input probability of an instability event (crash, hang, driver timeout) binary classification

The decision rule recommends the candidate with the highest predicted gain among those whose predicted instability risk is below a threshold \tau:

c^* = \arg\max_{c} \; \widehat{\text{gain}}(c) \quad \text{subject to} \quad \hat p_{\text{unstable}}(c) < \tau.

This keeps stability as a constraint, matching the business goal, rather than something a large performance gain can trade away. Problem 44 compares this with a single weighted score.

Workload classification fits as an upstream model. Its input is a window of telemetry (utilization, memory traffic, power). Its output is a workload class, such as compute-heavy, memory-bound, or ray-tracing heavy. That class becomes an input feature to both models above, and it lets the system reuse what it learned about one game for others of the same class.

Alternative framings worth naming: a single regression of “stable gain” that is zero when a run is unstable (simpler, but it hides why a configuration was rejected), or treating tuning as black-box optimization that searches the configuration space with real test runs (accurate, but each test run is expensive and may crash a system).

Answer. Use a regression model for performance gain and a binary classifier for instability risk, both taking (GPU, workload, configuration) as input. Recommend the highest predicted gain subject to \hat p_{\text{unstable}} < \tau. Add a workload classifier upstream whose output feeds both models.

Problem 3: What kind of data is each telemetry field?

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 1, Data types and encoding categorical features.

A telemetry record contains: GPU core clock (MHz), board power (W), hotspot temperature (°C), number of driver timeouts in the last hour, GPU model (one of 300 SKUs), a stability grade from validation (“fail”, “marginal”, “pass”), and workload type (one of 6). Classify each field by the book’s data types and choose an encoding for each.

TipWorked solution

The book first separates structured data, which follows a fixed schema of rows and columns, from unstructured data such as text, images, and audio. Every field here is structured, which already hints at the model family that suits it (tree models, Problem 33).

Structured data is then split into numerical (continuous: any value in a range; discrete: only distinct values such as counts) and categorical (nominal, with no order, or ordinal, with an order). The type decides the encoding.

Field Type Encoding
Core clock (MHz) numerical, continuous scale it (Problem 4)
Board power (W) numerical, continuous scale it
Hotspot temperature numerical, continuous scale it, or bucket it (Problem 34)
Driver timeouts per hour numerical, discrete scale it, log-scaling it first if it is skewed
GPU model (300 SKUs) categorical, nominal a learned embedding
Stability grade categorical, ordinal integer encoding: fail = 0, marginal = 1, pass = 2
Workload type (6 values) categorical, nominal one-hot encoding

The reasoning behind the categorical choices:

  • Integer encoding gives each category a number. It suits the stability grade because its values have a real order, and the integers preserve that order: “marginal” sits between “fail” and “pass”.
  • One-hot encoding creates one binary column per category, with a 1 in the column of the value present. It suits workload type. Integer-encoding workload type would be a mistake: if memory-bound = 1 and ray-tracing heavy = 5, the model would treat ray tracing as “five times” memory-bound and as closer to category 4 than to category 1, an order and distance that do not exist. One-hot avoids this, and 6 values make only 6 columns.
  • An embedding maps each category to a short learned vector of real numbers, trained along with the model. It suits the GPU model. One-hot with 300 values would give 300 columns, almost all zero, and nothing would tell the model that two SKUs are related. With an embedding, SKUs that behave alike (same architecture, similar memory) end up with similar vectors. That helps the model generalize to a SKU with little data, which is part of the project’s “generalize across hardware generations” goal.

Answer. Clock, power, and temperature are continuous numerical. Timeouts are discrete numerical. GPU model and workload type are nominal categorical. Stability grade is ordinal categorical. Encode the GPU model with an embedding, workload type with one-hot, the stability grade with integers, and scale the numerical fields.

Problem 4: Scaling telemetry features

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 1, Feature scaling.

Five test runs recorded board power of 150, 200, 250, 300, and 350 W. Apply min-max normalization and z-score standardization to these values (use the population standard deviation). Then four GPUs logged 1, 2, 10, and 1,000 instability events over a month. Apply log scaling (natural log) and explain why it helps.

TipWorked solution

Many models learn poorly when features sit on very different ranges, or when one feature has a long tail. Feature scaling fixes the range or the shape.

Min-max normalization maps values to [0, 1]:

z = \frac{x - x_{\min}}{x_{\max} - x_{\min}} = \frac{x - 150}{200}.

That gives 0,\; 0.25,\; 0.5,\; 0.75,\; 1.

Standardization gives mean 0 and standard deviation 1: z = (x - \mu)/\sigma. The mean is \mu = 250. The deviations are -100, -50, 0, 50, 100, so

\sigma = \sqrt{\frac{100^2 + 50^2 + 0 + 50^2 + 100^2}{5}} = \sqrt{5000} \approx 70.7.

That gives z \approx -1.41,\; -0.71,\; 0,\; 0.71,\; 1.41.

Min-max keeps the shape of the distribution and only changes its range. Standardization centers and rescales it.

Log scaling of the event counts with z = \ln x:

Events 1 2 10 1,000
\ln x 0 0.69 2.30 6.91

The raw values span three orders of magnitude, so one GPU with 1,000 events would dominate any distance or gradient computed on them. After the log they span about 7 units. That makes the distribution less skewed and helps optimization converge.

A practical note: \ln 0 is undefined, and many GPUs will log zero events. The usual fix is \ln(1 + x).

Answer. Min-max: 0, 0.25, 0.5, 0.75, 1. Z-scores: about -1.41, -0.71, 0, 0.71, 1.41. Log of the event counts: 0, 0.69, 2.30, 6.91. The log compresses a heavy tail, and \ln(1+x) handles zero counts.

Problem 5: Tickets with missing fields

Inspired by Project 18 (context and intent pre-check). Book: Chapter 1, Handling missing values.

The pre-check’s training data is built from 40,000 historical tickets. 30% have no “steps to reproduce” field, 5% have no component label, and a few tickets are missing almost every field. Apply the book’s two strategies for missing values to this data, and point out what is unusual about missing data in this particular project.

TipWorked solution

The book gives two strategies for missing data.

Deletion.

  • Row deletion drops records with many missing values. The few near-empty tickets are reasonable to drop from training, since there is little to learn from them.
  • Column deletion drops a feature that is mostly missing. “Steps to reproduce” is missing 30% of the time, which is a lot, but not enough to justify dropping the column.

The cost of deletion is less training data.

Imputation. Fill the gap with a default value, or with a summary of the observed values. Which summary depends on the field:

  • the mean for a numerical field with a roughly symmetric distribution,
  • the median for a skewed numerical field (for example, ticket length in words, where a few very long tickets would drag the mean up),
  • the mode, the most common value, for a categorical field, where a mean has no meaning.

A missing component label is categorical, so it could be filled with the mode (the most common component), or better, predicted from the files the ticket mentions. The cost is noise: an imputed value can look like real information.

What is unusual here. For this project, the fact that a field is missing is itself evidence. A bug report with no steps to reproduce is exactly what the pre-check should catch, because an agent may not be able to act on it. Two consequences follow:

  • Do not delete or silently impute fields whose absence is a signal of insufficiency. Imputing “steps to reproduce” would erase the most useful clue.
  • Keep a binary “field is missing” indicator as a feature, alongside any imputed value. (This goes slightly beyond the book’s two strategies, and it is standard practice when missingness carries meaning.)

The general lesson for interviews: before choosing deletion or imputation, ask whether missingness is random noise or part of what we want to predict.

Answer. Drop near-empty rows, keep the 30%-missing column, and impute low-stakes gaps like the component label. Do not impute fields whose absence signals an insufficient ticket. Add missing-field indicators instead, because here missingness is a signal, not just noise.

Problem 6: Where do failure labels come from?

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 1, Constructing the dataset.

We want a model that labels each failed agent run with the stage that caused it: dropped requirement, wrong context, planning error, tool error, or agent error. We have 18 months of run logs. Compare hand labeling with natural labeling for this task, propose a sampling plan, and say how to split the data.

TipWorked solution

The book names two ways to get labels.

  • Hand labeling. Experts read a failed run and assign the stage. The labels are accurate, but the book lists five drawbacks, and all apply here. It is expensive and slow (an expert may need twenty minutes per trace). It needs domain knowledge (only engineers who know the codebase can tell a planning error from a context error). It introduces bias (each expert has a favourite explanation, and different experts disagree). And it is a privacy risk (annotators must read proprietary code and tickets).
  • Natural labeling. Labels are inferred automatically from what happened, with no annotator. Here, natural signals tell us whether a run failed (the build broke, tests failed, the reviewer rejected it). They rarely tell us which stage caused it, because a red test does not say whether the plan or the context was wrong.

So the two work together. Natural labels mark which runs failed, cheaply and at scale. Hand labels assign the failure stage to a sample of those runs. The project’s own success criterion, attribution that agrees with experts, also needs an expert-labelled evaluation set.

Sampling. We cannot afford expert labels on every failed run, so we must choose which runs the experts see. A sampling strategy is the rule for that choice. The book names five. Each one, applied to our 18 months of logs:

Strategy How it works Applied here Verdict
Convenience sampling take whatever data is easiest to get label the last month’s runs, or only the team that already exports clean traces cheap, but unrepresentative: one team’s or one month’s failures are not everyone’s
Snowball sampling start from a few examples and add the examples linked to them start from a known dropped-requirement failure, then add its re-runs and linked tickets good for finding rare connected cases, but the sample clusters around its seeds
Stratified sampling split the population into groups (strata) and sample from each group separately strata = repository × feature type; sample a fixed number of failed runs from each chosen: every repository and feature type is guaranteed to appear
Reservoir sampling keep a fixed-size uniform random sample from a stream of unknown length: the n-th item enters the reservoir with probability k/n, replacing a random member keep a uniform sample of 500 failed runs as new runs stream in useful for ongoing collection after launch, but a uniform sample copies the skew: rare stages stay rare
Importance sampling sample from a different distribution than the real one, then weight each example by (real probability) / (sampling probability) oversample rare stages, then down-weight them when computing overall metrics the correction that makes oversampling honest

Why stratified wins: we already know the groups that matter (repositories and feature types), and the danger is that a big, busy repository crowds the others out. Stratifying guarantees coverage of each group. Inside each stratum we then oversample the rare failure stages so each has enough labelled examples to evaluate. Oversampling distorts the stage frequencies, so when we report an overall accuracy we use importance weights to undo the distortion. For example, if “dropped requirement” makes up 5% of real failures but 20% of the labelled sample, each such example gets weight 0.05 / 0.20 = 0.25.

Splitting. The dataset is divided three ways. The training set fits the model’s parameters. The validation set is used to choose hyperparameters and thresholds. The test set is touched once, at the end, to estimate real-world performance.

How the runs are assigned matters as much as the proportions. Split by time: train on older runs and evaluate on newer ones. A random split would place runs from the same feature, or from the same week’s agent version, on both sides. That leaks information and makes the model look better than it will be on next month’s runs. The project brief itself specifies a time split for its gold set.

Answer. Use natural signals to find failed runs, and expert hand labels to assign the failure stage. Choose runs for labelling by stratified sampling over repository and feature type, rather than convenience, snowball, or uniform reservoir sampling, because it guarantees every group is covered. Oversample rare stages within each stratum and correct overall metrics with importance weights. Split into train, validation, and test by time, not at random.

Problem 7: Instability is rare

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 1, Address any class imbalances.

Of 100,000 validation runs, 2% ended in an instability event. (a) What accuracy does a model get by always predicting “stable”? (b) How many examples remain if we undersample the majority class to a 1:1 ratio, and how many copies of each unstable run are needed to oversample to 1:1? (c) Compute class weights with w_c = N / (K \, n_c), where K is the number of classes.

TipWorked solution

The counts are 2,000 unstable runs (the minority class) and 98,000 stable runs (the majority class).

(a) Always predicting “stable” is right 98,000 times out of 100,000, so accuracy is 98%. It never catches an instability, which is the only thing that matters. That is why accuracy alone is a poor metric on imbalanced data (Problem 26).

(b) Resampling changes the class ratio.

  • Undersampling keeps all 2,000 unstable runs and 2,000 of the stable ones: 4,000 examples. We discard 96,000 stable runs, 98% of that class, along with whatever they could have taught us.
  • Oversampling keeps all 98,000 stable runs and repeats each unstable run 98{,}000 / 2{,}000 = 49 times. The model may then memorize those 2,000 runs, because it sees each one 49 times.

(c) Altering the loss function is the book’s other approach. Resampling changes which examples the model sees. Altering the loss keeps every example but changes how much each mistake costs.

A class weight w_c is a number attached to every example of class c. It multiplies that example’s term in the loss. The stability model is a binary classifier, so its usual loss is binary cross-entropy: for an example with label y_i (1 = unstable) and predicted probability \hat p_i, the loss is -[y_i \ln \hat p_i + (1-y_i)\ln(1-\hat p_i)]. Weighted cross-entropy multiplies each example’s term by the weight of its true class:

L = -\frac{1}{N}\sum_{i=1}^{N} w_{y_i}\big[\,y_i \ln \hat p_i + (1-y_i)\ln(1-\hat p_i)\,\big]

The formula w_c = N/(K\,n_c) makes a class’s weight inversely proportional to its size n_c:

w_{\text{stable}} = \frac{100{,}000}{2 \times 98{,}000} \approx 0.51, \qquad w_{\text{unstable}} = \frac{100{,}000}{2 \times 2{,}000} = 25.

Two ways to see what this does:

  • Per mistake. Suppose the model gives an unstable run \hat p = 0.1 (a miss). Its unweighted loss is -\ln 0.1 = 2.30, and weighted it is 25 \times 2.30 = 57.6. A false alarm on a stable run at \hat p = 0.9 also has unweighted loss -\ln 0.1 = 2.30, but weighted it is only 0.51 \times 2.30 = 1.17. The same-sized mistake now costs 49 times more on the minority class.
  • Per class. Total weight is 98{,}000 \times 0.51 \approx 50{,}000 for stable runs and 2{,}000 \times 25 = 50{,}000 for unstable runs. Each class now contributes equally to the loss, so the model can no longer get a low loss by ignoring the minority class.

The gradient is scaled by the same weight, so in expectation weighting an unstable run by 49 relative to a stable one has the same effect as seeing it 49 times (oversampling). The difference is that nothing is copied or discarded. It does not remove the memorization risk: the model still learns the minority class from only 2,000 distinct runs.

A side effect to remember. A weighted model’s probabilities are pushed toward the minority class, so an output of 0.5 no longer means “a 50% chance of instability”. Either recalibrate afterwards (Problem 38) or choose the decision threshold on validation data (Problem 26), rather than reading the raw output as a probability.

The book names two refined losses for the same purpose:

  • Class-balanced loss sets weights from the effective number of samples in each class rather than the raw count. The idea is that extra examples of a large class are increasingly redundant, so the very large class is not down-weighted as harshly as 1/n_c would.
  • Focal loss weights each example by how wrong the model currently is, not by its class. With p_t the probability assigned to the true class, it multiplies the cross-entropy term by (1 - p_t)^{\gamma}, typically with \gamma = 2. An easy example with p_t = 0.9 is scaled by 0.1^2 = 0.01, while a hard one with p_t = 0.1 keeps 0.9^2 = 0.81 of its loss. On imbalanced data most easy examples belong to the majority class, so training shifts toward the rare, hard cases.

For this project, a missed instability crashes a user’s system, so the threshold should also be chosen with that cost in mind (Problem 26).

Answer. (a) 98% accuracy, while catching no instabilities. (b) Undersampling leaves 4,000 examples. Oversampling repeats each unstable run 49 times. (c) w_{\text{stable}} \approx 0.51 and w_{\text{unstable}} = 25. Each weight multiplies that class’s terms in a weighted cross-entropy loss, so a mistake on an unstable run costs 49 times as much and the two classes contribute equally to the total loss.

Problem 8: Choosing models, starting from baselines

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 1, Model selection and Model training.

Walk through how you would choose a model for “predict which stage caused a failed agent run.” The project already defines two baselines: free-text plans, and blind retry with the same retry budget. Also say when you would fine-tune rather than train from scratch, and when distributed training would come up.

TipWorked solution

The book’s model-selection process has four steps.

  1. Establish a simple baseline. For attribution, a baseline could be “always predict the most common stage”, or a few rules (“the build failed, so blame the tool stage”). For the repair loop, the project’s baselines are free-text plans and blind retry at an equal retry budget. Any proposed system must beat these, and keeping the budget equal makes the comparison fair.
  2. Try simple models. Logistic regression, or gradient-boosted trees, on hand-built trace features: which step failed first, number of tool errors, whether requirements were linked to code changes, test outcomes. These train fast and are easy to interpret.
  3. Move to complex models if needed. A neural network that reads the trace text, or a fine-tuned LLM classifier, can pick up patterns that hand-built features miss.
  4. Consider an ensemble if accuracy still falls short. An ensemble combines several models’ predictions. The book names three kinds:
    • Bagging trains many copies of one model type in parallel, each on a different random resample of the training data, and averages or votes their predictions. It reduces variance, meaning sensitivity to the particular training sample. A random forest is bagged decision trees.
    • Boosting trains weak models in sequence, each one focusing on the examples the previous ones got wrong. It reduces bias (systematic underfitting) as well as variance. Gradient-boosted trees are the standard example.
    • Stacking trains different model types (say, a logistic regression and a tree model), then trains a small “meta-model” that takes their predictions as inputs and learns how to combine them.
    Problem 33 compares bagging and boosting in more depth.

The book’s checklist for comparing candidates applies directly: how much data each needs (expert labels are scarce), training speed, the hyperparameters to tune, compute cost, latency, and interpretability. Interpretability matters a lot here, because a diagnosis is only useful if the feedback generator can explain it.

Fine-tuning or training from scratch? With a few thousand labelled failures, fine-tune a pretrained language model on trace text. Training from scratch would need far more data. Fine-tuning means continuing to train a pretrained model with small updates to its parameters.

Distributed training comes up if we fine-tune a large model on many long traces. Data parallelism copies the model to each GPU and splits the batches. Model parallelism splits the model itself across GPUs when it is too large for one.

Answer. Start from the project’s baselines and a majority-class or rule baseline. Try simple interpretable models on trace features, then a fine-tuned language model if needed, and ensembles last. Fine-tune rather than train from scratch because labels are scarce. Use data or model parallelism only if model size or data volume demands it.

Problem 9: Offline and online metrics for a tuning system

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 1, Evaluation.

Propose offline metrics for the performance model and the stability model from Problem 2, and online metrics for the tuning system once it ships. Then adapt the book’s “fairness and bias” talking point to this project.

TipWorked solution

Offline metrics score predictions against held-out data during development. They depend on the task type.

  • Performance model (regression): the book’s regression metrics are MSE, MAE, and RMSE. With prediction errors e_i = y_i - \hat y_i:
    • MAE (mean absolute error) = \frac{1}{n}\sum |e_i|: the average size of a miss, in the target’s own unit (percentage points of gain).
    • MSE (mean squared error) = \frac{1}{n}\sum e_i^2: squares each error, so large misses count disproportionately. Its unit is squared percent, which is hard to read.
    • RMSE = \sqrt{\text{MSE}}: back in percent, but still dominated by the largest misses.
    For errors of (1, 1, 1, 9) points, MAE = 3 while RMSE = \sqrt{84/4} \approx 4.6. Report MAE because it is easy to explain (“off by 3 points on average”). Watch RMSE as well, because one wildly over-predicted gain could tempt the system into a bad configuration.
  • Stability model (classification): recall (of the truly unstable runs, the fraction the model flags), precision (of the runs it flags, the fraction truly unstable), and PR-AUC, which summarizes the precision–recall trade-off over all thresholds. Problem 26 works these through and shows why PR-AUC beats accuracy here.
  • How to split: hold out whole GPU architectures and workloads, not random runs. The project explicitly asks how models generalize across hardware generations, and a random split would hide that weakness.

Online metrics measure impact after deployment and tie back to the business goal. Choosing them involves product judgement.

  • Average performance gain on users’ real workloads.
  • Power efficiency, such as frames per second per watt, since the project lists it explicitly.
  • Instability incident rate among systems using tuned settings, compared with untuned systems.
  • Revert rate: how often users switch the tuning off.

Fairness and bias, adapted. The book asks whether a model performs worse for some groups. Here the “groups” are hardware generations, SKUs, and workload types. A model trained mostly on popular new GPUs can be accurate on average while being unsafe on an older or rarer SKU. So report every metric per architecture and per workload class, and gate the release on the worst group, not the average.

The book also asks what happens if someone malicious gets access to the system. The analogous risk here is a model that can be pushed into recommending unsafe voltages. That argues for hard safety limits outside the model (Problem 31).

Answer. Offline: MAE for predicted gain, plus recall, precision, and PR-AUC for instability, all on held-out architectures and workloads. Online: performance gain, performance per watt, instability incident rate, and revert rate. Report per architecture and workload, and gate on the worst case.

Problem 10: Where and how should the tuner run?

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 1, Deployment and Serving; Monitoring.

The tuning model could run in the cloud, or locally inside the graphics driver software on the user’s PC. Compare the two using the book’s cloud versus on-device trade-offs. Say which compression techniques might be needed, whether predictions should be batch or online, and what happens when a new GPU generation ships.

TipWorked solution

Cloud vs on-device. The book compares them on several axes.

Axis Cloud On-device (driver-side)
Simplicity easier to deploy and update harder: ships with driver releases
Cost server cost per request none
Network latency present none
Inference latency usually lower: powerful servers usually higher: the user’s CPU is weaker and shared with the game
Hardware constraints few must fit a small CPU and memory budget and not slow the game
Privacy telemetry leaves the machine telemetry stays local
Internet dependency needs a connection works offline

A tuner reacting to live telemetry on a gaming PC suits on-device inference: no round trip, it works offline, and users’ telemetry stays private. The price is the two rows where on-device loses: slower inference and tight hardware limits. Compression addresses both. Training stays in the cloud, on aggregated, consented telemetry.

Compression. On-device means small and fast, and the book lists three techniques:

  • knowledge distillation: train a small “student” model to reproduce the outputs of a large, accurate “teacher” model. The student learns from the teacher’s full probability outputs, which carry more information than hard labels.
  • pruning: find the least useful weights (for example, those closest to zero) and set them to zero. The resulting sparse model can be stored and run more cheaply.
  • quantization: store each parameter in fewer bits. Going from 32-bit floats to 8-bit integers makes the model 4 times smaller and usually faster. It can be applied after training (post-training quantization) or simulated during training (quantization-aware training), which usually loses less accuracy.

A small gradient-boosted tree model may need none of these. A neural network probably would.

Batch or online?

  • Batch: precompute a recommended configuration per (SKU, workload class) and ship it as a lookup table. This is cheap and predictable, but it cannot react to a particular unit’s temperature or silicon.
  • Online: predict from live telemetry. This is more adaptive, but the computation has to happen while the user is running something.

A hybrid is natural: a batch default per (SKU, workload), refined online within safe limits.

New GPU generation. This is data distribution shift: the deployed model meets inputs unlike its training data. The book’s remedies are to train on large, diverse datasets and to retrain regularly on labelled data from the new distribution. Here that means collecting validation runs on the new generation before enabling tuning, and monitoring stability per architecture once it ships.

Answer. Run inference on-device, for latency, offline use, and privacy, and train in the cloud. Compress with distillation, pruning, or quantization if the model is a neural network. Use batch defaults per SKU and workload, refined online. Treat a new GPU generation as distribution shift: collect data on it first, retrain, and monitor.

Problem 11: Rolling out the pre-check safely

Inspired by Project 18 (context and intent pre-check). Book: Chapter 1, Test in production; Monitoring.

The pre-check model passes offline evaluation. Describe how to test it in production, why shadow deployment is a natural first step here, what an A/B test then needs, and what to monitor afterwards.

TipWorked solution

The book’s point is that only real traffic shows how a model performs in production. It lists shadow deployment, A/B testing, canary releases, interleaving, and bandits.

Shadow deployment first. Every ticket goes to both the existing path (everything passes to the agent) and the new pre-check. Only the existing path takes effect: the pre-check’s decision is logged, not enforced. Later we compare: for tickets the pre-check would have held, did the agent actually fail or produce a rejected fix?

Shadow mode suits a gate like this because a wrong hold has a real cost: it blocks an engineer’s work. Shadow mode measures the decision quality with no risk to anyone. The cost the book names is doubled computation, since both paths run on every request. (The project brief also starts with shadow mode.)

Then an A/B test. Route a fraction of tickets through the pre-check for real. Two requirements from the book:

  1. Random assignment of tickets (or teams) to each arm, so the arms are comparable.
  2. Enough data points for the difference to be trustworthy.

Measure agent fix quality on passed tickets, wasted agent runs, reviewer time, and how often held tickets were overturned.

The other three methods the book names, and why they come later or not at all:

  • Canary release. Enable the new model for a small slice of traffic first (one team, or 1% of tickets), watch for problems, then widen step by step. It limits the damage if the model misbehaves, but the slice is usually chosen for convenience rather than at random, so it is a safety step, not a clean comparison. It is a gentle alternative here when randomizing tickets is awkward.
  • Interleaving. Built for ranking systems: merge the results of two rankers into one list shown to the same user, then see which ranker’s items get used. Each user acts as their own control, so it needs far less traffic than an A/B test. It does not fit a pass-or-hold gate, which makes one decision per ticket and has nothing to interleave. It would fit the context ranker (Problem 12).
  • Bandits. A multi-armed bandit shifts traffic toward whichever variant is performing better while the test runs, so fewer tickets go through the worse variant. It needs a reward that arrives quickly, and ticket outcomes take days to become known (Problem 38). So a fixed A/B split is the better fit here.

Monitoring after launch. The book splits this in two.

  • Operational metrics: latency of the decision, throughput, error rate, compute usage.
  • ML-specific metrics: the distribution of inputs (ticket length, fraction with missing fields), the distribution of outputs (hold rate), accuracy against later outcomes, and the deployed model version.

A sudden jump in the hold rate signals drift, for example when a team adopts a new ticket template. That is concept drift or input distribution shift, and the remedy is retraining on recent labelled data.

Answer. Shadow-deploy first: log the pre-check’s decisions without enforcing them, and compare them with actual agent outcomes. Then A/B test with random assignment and enough tickets, or canary with one team. Monitor operational metrics plus input and output distributions, hold rate, accuracy against outcomes, and model version.

Problem 12: Context discovery as representation learning

Inspired by Project 18 (context and intent pre-check). Book: Chapter 2, Frame the Problem and Model training.

For each ticket, the pre-check must find the most relevant code files, documents, and past tickets. Frame this as an ML task the way the book frames visual search. Then compare three sources of “positive” (relevant) examples for training: human judgement, interaction data, and self-supervision.

TipWorked solution

Framing. The output is a ranked list of items, ordered by relevance to the ticket, so this is a ranking problem. The book solves ranking with representation learning:

  1. Train an encoder that maps each ticket, and each file, document, or past ticket, to an embedding vector.
  2. Train it so relevant pairs land close together in embedding space.
  3. At query time, embed the ticket, find the nearest items, and rank them by similarity.

Training uses contrastive learning. Each training example is a query (the ticket), one positive item, and several negatives. The model learns to score the positive above the negatives (Problem 13). The hard part is choosing positives. The book compares three sources.

Source Here Strength Weakness
Human judgement engineers mark which files are relevant to a ticket accurate slow and expensive
Interactions files edited in the commit that fixed the ticket, or docs the engineer opened automatic, plentiful noisy: a fix touches incidental files, and some relevant files are only read, never edited
Self-supervision create a positive by transforming the query, for example pairing a ticket’s title with its own body free, and not noisy does not match the real task: real positives are different items, not rewordings

In the book’s image setting, self-supervision wins: there are billions of images, and augmenting an image always yields a similar image. Here the balance is different. Interaction data is unusually good, because the fixing commit is close to a definition of “relevant context”. A sensible plan is to start from fix commits, filter obviously incidental files (lockfiles, formatting-only changes), and use a small human-judged set to evaluate.

As the book suggests, starting from a pretrained text or code encoder and fine-tuning it is much cheaper than training from scratch.

Answer. Frame it as ranking via representation learning: embed tickets and items, then rank items by similarity. Train with a contrastive loss. Use files changed in the fixing commit as positives (filtered for noise), and keep human judgement for the evaluation set. Self-supervision is free but does not match the real task.

Problem 13: A contrastive loss by hand

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 2, Choosing the loss function.

To build requirement-to-code traceability, we train embeddings so a requirement lands near the code diff that implements it. For one requirement, the dot-product similarities with four candidate diffs are: the true diff 2.0, and three other diffs 1.0, 0.5, and -1.0. Compute the contrastive loss using the book’s three steps. Then recompute it after training raises the true diff’s similarity to 4.0.

TipWorked solution

The book computes a simplified contrastive loss in three steps.

  1. Similarities. Use the dot product or cosine similarity between the query and each candidate embedding. (Euclidean distance tends to work poorly in high dimensions, a symptom of the curse of dimensionality.)
  2. Softmax turns the similarities into probabilities that sum to 1.
  3. Cross-entropy against the label “the true diff is the right answer” gives -\ln p_{\text{true}}.

Before training. Similarities (2.0, 1.0, 0.5, -1.0). The exponentials are 7.389,\; 2.718,\; 1.649,\; 0.368, which sum to 12.12.

p_{\text{true}} = \frac{7.389}{12.12} \approx 0.610, \qquad \text{loss} = -\ln 0.610 \approx 0.495.

After training. Similarities (4.0, 1.0, 0.5, -1.0). Now e^{4} = 54.60, and the sum is 59.33.

p_{\text{true}} = \frac{54.60}{59.33} \approx 0.920, \qquad \text{loss} = -\ln 0.920 \approx 0.083.

The loss falls as the true diff becomes clearly more similar than the others. Gradient descent on this loss pulls the requirement and its diff together and pushes the requirement away from the other diffs.

Two practical points for interviews:

  • Negatives matter. Diffs from unrelated repositories are easy negatives that teach little. Diffs from the same feature branch are hard negatives that teach the fine distinctions. Problem 41 returns to this.
  • What the trained model gives Project 19. For any requirement we can now rank diffs by similarity. A requirement with no diff above a threshold is flagged as possibly dropped, which is one of the failure types in the project’s fault model.

Answer. Before training: p_{\text{true}} \approx 0.610 and loss \approx 0.495. After: p_{\text{true}} \approx 0.920 and loss \approx 0.083.

Problem 14: Which ranking metric for retrieved context?

Inspired by Project 18 (context and intent pre-check). Book: Chapter 2, Offline metrics.

For one ticket, the context search returns five items. An engineer rates their relevance on a 0 to 3 scale: (0, 3, 1, 0, 2), in ranked order. One more relevant item exists that was not retrieved. Treating any rating above 0 as “relevant”, compute the reciprocal rank, precision@5, recall@5, and average precision. Then compute nDCG@5 using the graded ratings. Which metric suits this system?

TipWorked solution

The relevant items (rating above 0) sit at ranks 2, 3, and 5. Four relevant items exist in total, counting the one that was not retrieved.

Reciprocal rank. The first relevant item is at rank 2, so RR = 1/2 = 0.5. MRR averages this over many queries. It ignores every relevant item after the first.

Precision@5 = 3/5 = 0.6. Recall@5 = 3/4 = 0.75. Neither cares about order within the top 5.

Average precision. Average the precision at each rank that holds a relevant item:

P@2 = \tfrac{1}{2},\quad P@3 = \tfrac{2}{3},\quad P@5 = \tfrac{3}{5}

\text{AP} = \frac{0.5 + 0.667 + 0.6}{3} \approx 0.589.

(Some definitions divide by all 4 relevant items instead of the 3 retrieved. Say which one you use.) mAP averages AP over queries. It rewards relevant items near the top, but it treats relevance as binary.

nDCG@5 uses the graded ratings. DCG adds up each item’s rating divided by \log_2(i+1), where i is its rank:

\text{DCG} = \frac{0}{1} + \frac{3}{1.585} + \frac{1}{2} + \frac{0}{2.322} + \frac{2}{2.585} \text{DCG} = 0 + 1.893 + 0.5 + 0 + 0.774 = 3.167.

The ideal ordering (3, 2, 1, 0, 0) gives

\text{IDCG} = \frac{3}{1} + \frac{2}{1.585} + \frac{1}{2} = 4.762,

\text{nDCG} = 3.167 / 4.762 \approx 0.665.

This IDCG, like the book’s example, uses only the five retrieved ratings. The standard definition sorts every relevant item in the collection, including the one that was missed. Its rating is not given. If it were 1, then \text{IDCG} = 3 + 2/1.585 + 1/2 + 1/2.322 \approx 5.193 and nDCG@5 \approx 0.610.

Which to choose. The ratings are graded, and order matters: the agent’s context window is limited, so the top items matter most. Following the book’s logic, nDCG fits best when graded relevance is available. If only binary labels exist, such as “file was in the fixing commit”, mAP is the fallback. Recall@k is still worth watching separately, because a context item that is never retrieved can never help the agent.

Answer. RR = 0.5, P@5 = 0.6, R@5 = 0.75, AP \approx 0.589, nDCG@5 \approx 0.665 (with IDCG over the retrieved items only). Prefer nDCG because the ratings are graded and order matters. Use mAP for binary labels, and track recall@k as a coverage check.

Problem 15: Searching 10 million code chunks

Inspired by Project 18 (context and intent pre-check). Book: Chapter 2, Serving and nearest neighbor algorithms.

The context index holds N = 10^7 code and document chunks with D = 768-dimensional embeddings. (a) Estimate the cost of exact nearest neighbour search for one query, and the memory for the raw FP32 index. (b) Name the book’s families of approximate methods and what they trade away. (c) Sketch the indexing and prediction pipelines, including what the re-ranking step must enforce.

TipWorked solution

(a) Exact search. Compare the query with every vector: O(N \times D).

10^7 \times 768 = 7.68 \times 10^9 \text{ multiply-adds per query}.

At an assumed 10^{10} multiply-adds per second on a CPU, that is about 0.8 s per query. That is too slow for a pre-check that should answer in seconds while also doing other work.

Memory for the raw index:

10^7 \times 768 \times 4 \text{ bytes} \approx 30.7 \text{ GB}.

The book notes that vector quantization and product quantization shrink this.

  • Vector quantization clusters all vectors (for example with k-means) and stores each vector as the ID of its nearest cluster centre. That is tiny, but every vector in a cluster becomes identical.
  • Product quantization splits each 768-dimensional vector into, say, 96 sub-vectors of 8 dimensions. It runs vector quantization separately on each slice with 256 centres, so each slice is stored as a 1-byte centre ID. Each vector then takes 96 \times 1 = 96 bytes instead of 768 \times 4 = 3{,}072, a 32-fold saving, and the index takes about 0.96 GB. Distances are computed approximately from the centres, which trades a little accuracy for the memory saving.

(b) Approximate nearest neighbour search gives up the guarantee of the exact top results in exchange for sublinear search time. It needs preprocessing and extra memory. The book’s three families:

  • Tree-based: recursively split the space, then search only the query’s partition (R-trees, k-d trees, Annoy).
  • Locality-sensitive hashing: hash functions put nearby points in the same bucket, so only the query’s bucket is searched.
  • Clustering-based: group points into clusters, then search only the nearest cluster or clusters.

Libraries such as Faiss and ScaNN implement these. At 10^7 items, approximate search is the pragmatic choice.

(c) Pipelines.

  • Indexing: embed every chunk and store it in the index. Update incrementally when files change. Re-embed everything when the encoder is retrained, because old and new embeddings are not comparable.
  • Prediction: embed the ticket, run approximate search, then re-rank.

The re-ranking step plays the same role as the book’s business rules (“no private images”). Here it must enforce access control, so the agent never receives chunks from repositories the ticket’s author cannot see. It should also remove near-duplicate chunks and stale files.

Answer. (a) About 7.7 \times 10^9 multiply-adds per query (roughly 0.8 s at 10^{10} per second) and about 30.7 GB of FP32 vectors. (b) Tree-based, LSH, and clustering-based approximate search, trading exactness for sublinear time. (c) An indexing pipeline that updates incrementally and fully on retraining, and a prediction pipeline (embed, search, re-rank) whose re-ranker enforces permissions and removes duplicates.

Problem 16: Locating failures in a trace as detection

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 3, Frame the Problem and Model training.

An agent trace is a sequence of 200 steps. We want a model that outputs each failure as a step span plus a failure type: for example, “steps 41 to 55: wrong context”. Map this onto the book’s object-detection framing. Compare two-stage and one-stage designs, and write the training loss.

TipWorked solution

Framing. Object detection does two tasks.

  • Localization, a regression task: in an image, predict a box (x, y, w, h). In a trace, predict a span (start step, length).
  • Classification, a multiclass task: in an image, the object class. In a trace, the failure type (dropped requirement, wrong context, planning, tool, agent).

A trace is a one-dimensional “image” whose pixels are steps.

Two-stage vs one-stage.

  • Two-stage: a proposal network suggests candidate spans likely to contain a failure, then a classifier labels each proposal. This is the book’s R-CNN family. It is usually more accurate, but slower, because the two models run in sequence.
  • One-stage: a single network predicts spans and types together (the YOLO and SSD family). It is faster, and usually a little less accurate.

The book chooses two-stage for a dataset of moderate size where latency does not matter. Failure analysis runs after a run finishes, offline, so the same reasoning applies: start with two-stage, and switch to one-stage if trace volume grows or diagnosis must happen during the run.

Loss. Combine a regression loss on span coordinates with a classification loss on types.

L_{\text{reg}} = \frac{1}{M}\sum_{i=1}^{M} \big[(s_i - \hat s_i)^2 + (\ell_i - \hat \ell_i)^2\big]

Here s_i is a span’s start and \ell_i its length.

L_{\text{cls}} = -\frac{1}{M}\sum_{i=1}^{M}\sum_{c=1}^{C} y_{i,c}\,\ln \hat y_{i,c}

L = L_{\text{cls}} + \lambda\, L_{\text{reg}}

The balancing weight \lambda sets how much span accuracy matters relative to type accuracy. It is a hyperparameter tuned on validation data.

For Project 19, both outputs matter. The span tells the repair loop which stage to re-run, and the type tells it what feedback to send.

Answer. Treat each failure as an “object”: regress its step span and classify its type. Start with a two-stage design (propose spans, then classify), because diagnosis runs offline. Train with cross-entropy plus \lambda times a regression loss on the span coordinates.

Problem 17: IoU, precision, and AP over step spans

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 3, Evaluation.

A trace has two true failure spans of type “wrong context”: steps 10 to 19 and steps 40 to 49 (inclusive). The model predicts six spans: A = 12 to 19, B = 5 to 14, C = 41 to 50, D = 44 to 55, E = 18 to 27, F = 60 to 65. Compute each prediction’s IoU with its best-matching true span. Then compute precision at IoU thresholds 0.7, 0.3, and 0.1, and the book’s average precision across those thresholds. If a second failure type has AP 0.5, what is mAP?

TipWorked solution

IoU (intersection over union) is the overlap divided by the combined extent. For inclusive step spans, count steps.

Prediction Best true span Intersection Union IoU
A: 12 to 19 10 to 19 8 10 0.800
B: 5 to 14 10 to 19 5 15 0.333
C: 41 to 50 40 to 49 9 11 0.818
D: 44 to 55 40 to 49 6 16 0.375
E: 18 to 27 10 to 19 2 18 0.111
F: 60 to 65 none 0 0

Precision at a threshold counts a prediction as correct when its IoU reaches the threshold.

  • At 0.7: A and C are correct, so precision = 2/6 \approx 0.333.
  • At 0.3: A, B, C, and D are correct, so precision = 4/6 \approx 0.667.
  • At 0.1: A, B, C, D, and E are correct, so precision = 5/6 \approx 0.833.

Precision depends heavily on the threshold, which is why one threshold alone is hard to interpret.

Average precision, in the book’s simplified version, averages precision over the thresholds:

\text{AP} = \frac{0.333 + 0.667 + 0.833}{3} \approx 0.611.

mAP averages AP over failure types:

\text{mAP} = \frac{0.611 + 0.5}{2} \approx 0.556.

Two refinements are worth naming in an interview. Standard benchmarks define AP as the area under the precision–recall curve at a fixed IoU, and COCO-style mAP then also averages over IoU thresholds. Benchmarks also match each true span at most once, so a duplicate detection of an already-matched failure counts as a false positive. That rule is why duplicate suppression matters (Problem 18).

Answer. IoUs: A 0.800, B 0.333, C 0.818, D 0.375, E 0.111, F 0. Precision is 0.333 at threshold 0.7, 0.667 at 0.3, and 0.833 at 0.1. AP \approx 0.611 and mAP \approx 0.556.

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 3, Overlapping bounding boxes.

Span Steps Score
P1 10 to 19 0.9

sort spans by score, highest first

    keep.append(best)
    remove best, and every remaining span with IoU(best, span) >= threshold

Problem 19: Growing and improving the training traces

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 3, Data augmentation and ML system design.

Only 3,000 failed traces have expert span labels. (a) How could data augmentation apply to traces, and should it happen offline or online? (b) After deployment, reviewers correct some diagnoses. How does the book’s hard negative mining use those corrections? (c) Why does the book run preprocessing and model inference as separate services, and does the same apply here?

TipWorked solution

(a) Augmentation. Data augmentation adds slightly modified copies of real examples. For images, that means crops, flips, and brightness changes. Traces have their own transformations that keep the label valid:

  • drop or duplicate uneventful steps outside the failure span,
  • shuffle the order of independent read-only steps,
  • paraphrase step text,
  • splice a labelled failure segment into a different successful trace.

The book’s caution carries over: when the input is transformed, the label must be transformed with it. Inserting steps before a failure shifts its span coordinates.

Offline or online? Offline augmentation precomputes the copies. Training is faster, but storage grows. Online augmentation creates them on the fly. It costs no storage, but slows each epoch. With only 3,000 traces, storage is cheap, so offline is fine.

(b) Hard negative mining. Hard negatives are examples the model got wrong, explicitly labelled and added back to the training set. When a reviewer says “the model blamed the tool stage, but the real cause was a dropped requirement”, that trace goes into the next training set with the corrected label. Retraining then targets exactly the cases the model currently confuses. The data pipeline that collects these corrections is how the system improves after launch.

(c) Separate services. In the book, preprocessing is CPU-bound and blurring (inference) needs a GPU. Separating them lets each scale independently and use its hardware well. The same split applies here: parsing raw logs into structured traces is CPU work, while running a large model over trace text uses GPUs. Separate services keep the GPUs busy instead of waiting on log parsing.

Answer. (a) Augment with label-preserving trace edits, shifting span labels when steps move. Offline is fine at this data size. (b) Add reviewer-corrected misdiagnoses back as labelled hard examples and retrain. (c) Separate the CPU-bound preprocessing from GPU inference so each scales and uses its hardware efficiently. The same applies to log parsing versus model inference.

Problem 20: Hybrid search for ticket context

Inspired by Project 18 (context and intent pre-check). Book: Chapter 4, Choosing the right ML category and Serving.

Engineers often paste exact error strings and function names into tickets. At other times they describe a problem in words that appear nowhere in the code. Design a context search that handles both cases, following the book’s video search architecture. Include what happens to documents that have no tags.

TipWorked solution

The book’s video search runs two searches in parallel and fuses them. That shape fits here because the two kinds of ticket need different tools.

1. Text (lexical) search. An inverted index maps each term to the documents containing it. A search engine such as Elasticsearch builds and queries it. This handles exact strings: an error message like ERR_DEVICE_LOST, or a function name, is found instantly. Inverted indexes involve no ML, so there is no training cost.

2. Semantic (embedding) search. A text encoder embeds the ticket, and approximate nearest neighbour search finds chunks with similar meaning (Problems 12 and 15). This handles “the screen flickers after waking from sleep” when the code talks about resume_from_d3.

3. Fusing layer. Combine the two ranked lists. The book’s simple option is a weighted sum of the two relevance scores. The alternative is a learned re-ranking model, which is more accurate but must be trained and is slower to serve. Start with the weighted sum and tune the weight on the evaluation set.

4. Re-ranking. Apply business rules: permissions, de-duplication, and preferring current files over deleted ones.

Indexing pipelines. One pipeline keeps the inverted index current. Another embeds new or changed chunks for the vector index.

Problem 22: Bag-of-words versus TF-IDF on three tickets

Inspired by Project 18 (context and intent pre-check). Book: Chapter 4, Text encoder: statistical methods.

Three normalized tickets:

  • d1: “fix crash on login”
  • d2: “login page crash”
  • d3: “add login button”
  1. Write d1 as a bag-of-words vector. (b) Compute TF-IDF weights for d1 using raw counts and \text{idf}(t) = \ln(N / \text{df}(t)). (c) Compute the cosine similarity of d1 and d2 under both representations. (d) Why would neither representation match “fix crash on login” with “resolve fault during sign-in”?
TipWorked solution

The vocabulary has 7 terms: fix, crash, on, login, page, add, button.

(a) Bag of words. Count each term: d1 = (1, 1, 1, 1, 0, 0, 0). Word order is lost, and the vector is sparse: one slot per vocabulary term, mostly zeros.

(b) TF-IDF down-weights terms that appear in many documents. With N = 3:

Term df idf
login 3 \ln(3/3) = 0
crash 2 \ln(3/2) \approx 0.405
fix, on, page, add, button 1 \ln 3 \approx 1.099

So d1 = (\text{fix } 1.099,\; \text{crash } 0.405,\; \text{on } 1.099,\; \text{login } 0). “login” appears in every ticket, so it tells us nothing and gets zero weight.

(c) Cosine similarity of d1 and d2.

Bag of words: they share crash and login, so the dot product is 2. The norms are |d_1| = 2 and |d_2| = \sqrt{3}.

\cos = \frac{2}{2\sqrt{3}} \approx 0.577.

TF-IDF: only “crash” contributes, so the dot product is 0.405^2 = 0.164. The norms are \sqrt{2(1.099)^2 + 0.405^2} \approx 1.606 and \sqrt{1.099^2 + 0.405^2} \approx 1.171.

\cos = \frac{0.164}{1.606 \times 1.171} \approx 0.087.

TF-IDF judges the two far less similar, because their main overlap was the uninformative word “login”.

(d) Both methods count exact words. “fix crash on login” and “resolve fault during sign-in” share no words, so both give similarity 0. The book lists the limitations of these statistical methods: they ignore word order (so “revert the fix” and “fix the revert” look identical), miss meaning, and produce sparse vectors. TF-IDF has one more cost: adding a new ticket changes the document frequencies, so the weights must be recomputed.

ML-based encoders fix this by learning dense vectors in which similar meanings land close together. The book names three, from simplest to most powerful:

  • Embedding (lookup) layer. A trainable table with one vector per token ID, learned along with the rest of the model for its task. It is simple and works well for IDs and short tags.
  • Word2vec. A shallow network trained on the idea that words appearing in similar contexts mean similar things. Its CBOW (continuous bag of words) variant predicts a centre word from the words around it. Its skip-gram variant predicts the surrounding words from the centre word. After training on many tickets, “crash” and “fault” appear near the same words (“on startup”, “stack trace”), so their vectors end up close. Each word gets exactly one vector, whatever its context.
  • Transformer-based models such as BERT. These read the whole sentence and give a word a different vector depending on its context, so “fault” in “segmentation fault” and in “not my fault” are told apart. They are the most accurate, and the slowest and largest.

For full ticket text, where context matters, the book’s choice of a transformer applies. For short tags, a lighter method is enough (Problem 46).

Answer. (a) (1,1,1,1,0,0,0). (b) fix 1.099, crash 0.405, on 1.099, login 0. (c) Cosine 0.577 with bag of words and about 0.087 with TF-IDF. (d) Both rely on exact word overlap and miss synonyms. Learned embeddings capture meaning: an embedding layer or word2vec gives one vector per word, and a transformer gives context-dependent vectors.

Problem 23: Evaluating search when there is one right answer

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 4, Offline metrics and Video encoder.

For each feature requirement, exactly one merged change implements it. A search model ranks changes for four requirements, placing the true change at ranks 1, 3, 15, and 50. A second model places them at 1, 3, 11, and 12. (a) Compute recall@10 and MRR for both models. (b) Why is precision@10 useless here? (c) To embed a whole agent trace, should we encode the full trace at once, or encode each step and average? Use the book’s video-level versus frame-level comparison.

TipWorked solution

(a) With one relevant item per query, recall@k becomes simply 1 if that item is in the top k and 0 otherwise.

  • Model 1: recall@10 = (1 + 1 + 0 + 0)/4 = 0.5.
  • Model 2: recall@10 = (1 + 1 + 0 + 0)/4 = 0.5.

Recall@10 cannot tell them apart, even though model 2 ranks the last two changes at 11 and 12 instead of 15 and 50. This is the book’s complaint: recall@k depends on k and gives 0 to anything just past the cutoff.

MRR averages 1/\text{rank}:

\text{MRR}_1 = \frac{1 + \tfrac13 + \tfrac1{15} + \tfrac1{50}}{4} = \frac{1.420}{4} \approx 0.355

\text{MRR}_2 = \frac{1 + \tfrac13 + \tfrac1{11} + \tfrac1{12}}{4} = \frac{1.508}{4} \approx 0.377

MRR rewards model 2 for ranking the true change higher, which is why the book picks MRR when each query has one relevant item.

(b) Precision@10 has at most one relevant item in its numerator, so it can never exceed 1/10 = 0.1, even for a perfect ranking. It barely varies between models.

(c) The book compares two video encoders.

  • Video-level: encode the whole video at once (3D convolutions or transformers). This captures temporal structure, but it is expensive.
  • Frame-level: sample frames, encode each, then aggregate, for example by averaging. This is cheaper and faster, but loses order.

For traces, order is the content. “Read the spec, then edited the file” and “edited, then read the spec” mean different things for diagnosing a planning failure. So per-step averaging is a cheap baseline for search, but a sequence-aware encoder over the trace (the video-level analogue) is the better choice when the task depends on order. The book makes the same call for videos only when temporal understanding is not crucial.

Answer. (a) Both models have recall@10 = 0.5. MRR is about 0.355 for model 1 and 0.377 for model 2. (b) Precision@10 is capped at 0.1 with one relevant item. (c) Per-step averaging is a cheap baseline, but because step order carries meaning, use a sequence-aware trace encoder.

Problem 24: Early or late fusion of ticket, code, and history

Inspired by Project 18 (context and intent pre-check). Book: Chapter 5, Late fusion and early fusion.

A ticket comes with three inputs: its text, the code files it references, and the history of related tickets. A ticket can look clear on its own while contradicting the current code. For example, it asks to “restore the old timeout” when the code’s comment says that timeout caused data loss. Compare late and early fusion for this case.

TipWorked solution

Late fusion processes each input with its own model, then combines the predictions.

  • Pros: each model can be trained, evaluated, and improved on its own.
  • Cons: each input needs its own labelled data. And it misses harm that only appears in combination.

The book’s example is a meme whose image and caption are each harmless alone but harmful together. Here, the ticket text alone looks sufficient, and the code alone looks fine, so both models would say “pass”. The conflict between them never reaches a model that could notice it.

Early fusion combines the features of all inputs first, then one model predicts from the joint representation.

  • Pros: only one model to label and train. It can learn that this combination is a problem.
  • Cons: learning cross-input relationships is harder and needs more training data.

The book chooses early fusion because combination effects are the point, and the platform has plenty of data. Here the deciding factor is the same: conflict detection is one of the project’s stated objectives, and conflict is by definition a property of a combination. So use early fusion: embed the ticket, the referenced code chunks, and the related history, then concatenate them (or let one model attend across them) and predict from the result.

If labelled data turns out to be too scarce for the joint model, a reasonable fallback keeps per-input models and adds an explicit cross-input feature, such as an “agreement score” between the ticket embedding and the code embedding, as a partial bridge.

Answer. Use early fusion. A conflict between ticket and code is a property of the combination, which late fusion cannot see because each input looks fine alone. The cost is a harder learning problem that needs enough training data.

Problem 25: Which classifier shape can explain a hold?

Inspired by Project 18 (context and intent pre-check). Book: Chapter 5, Choosing the right ML category.

When the pre-check holds a ticket, it must tell the author what is missing. The gap types are: no acceptance criteria, ambiguous scope, conflicting information, missing reproduction steps, and missing context. Compare the book’s four options (one binary classifier, one binary classifier per gap type, a multi-label classifier, and a multi-task classifier) and choose one.

TipWorked solution

Single binary classifier (sufficient or not). It is simple, but it cannot say which gap caused the hold. That breaks the explanation requirement. It also hides which gap types the model handles badly, so we cannot target improvements.

One binary classifier per gap type. Each model answers one question, such as “are acceptance criteria missing?”. It can explain, and each model can be monitored and improved independently. But five models must each be trained and maintained, which is expensive. Rare gap types also get little data.

Multi-label classifier. One model outputs a probability for each gap type, and a ticket can have several gaps at once. It is cheaper to train and maintain. Its weakness, per the book, is that every gap type shares one transformation of the input, while different gaps may need different features. “Conflicting information” needs code-versus-ticket comparison, while “missing reproduction steps” mostly needs the ticket text.

Multi-task classifier (the choice). Shared layers learn a common representation of the fused input (Problem 24). Then one small task-specific head per gap type transforms it as that gap needs.

  • One model to train, so it is cheap.
  • No redundant computation, because the expensive shared part runs once.
  • Training data for common gaps also improves the shared layers, which helps rare gaps.
  • Each head’s output names a specific gap, so it directly produces the explanation.

The decision. The ticket is held if any head’s probability exceeds its threshold. The explanation lists the gaps whose heads fired.

Answer. Use a multi-task classifier: shared layers plus one head per gap type. It explains holds by naming the gaps that fired, costs one model, and lets common gap types help rare ones. A single binary classifier cannot explain, and separate per-gap models cost too much to maintain.

Problem 28: Objectives that get gamed

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 6, Defining the ML objective.

The repair loop needs a training objective that defines a “successful run”. Candidates are: maximize the fraction of tests passing, maximize acceptance at first review, and minimize the number of retries. For each, describe how an agent could score well while doing worse work. Then propose a better objective, following the book’s reasoning about video recommendations.

TipWorked solution

The book weighs four objectives for video recommendations and names a loophole in two of them.

  • Maximize clicks rewards clickbait: a compelling thumbnail on a poor video.
  • Maximize completed videos rewards short videos, which are easy to finish.
  • Maximize watch time is better, but still a single proxy.
  • Maximize relevance, where relevance is defined by rules combining explicit and implicit signals (for example, “liked, or watched at least half”). The book chooses this one because it gives the most control over which signals count.

The same loopholes appear for agent runs, an instance of Goodhart’s law.

Proxy How it gets gamed
Fraction of tests passing weaken, skip, or delete tests, or implement only the easily tested part of the feature (the “clickbait” of agent runs)
Accepted at first review submit small, safe changes that skip hard requirements, much like short videos are easy to “complete”
Fewest retries stop early and submit something partial, rather than retry when retrying is warranted

A rule-defined success, in the book’s style: a run counts as successful when

  1. every requirement in the plan is traced to at least one code change and one test (the project’s traceability goal),
  2. pre-existing tests are unchanged and pass, along with the new ones,
  3. the reviewer accepts without a major-revision request.

Each rule closes one loophole. Rule 1 stops dropped requirements. Rule 2 stops test tampering. Rule 3 keeps a human judgement in the loop. Like the book’s relevance definition, it combines explicit signals (the reviewer’s verdict) with implicit ones (test and trace evidence), and the team controls which signals count.

Answer. Tests-passing rewards test tampering and partial features. First-review acceptance rewards small, safe changes. Fewest retries rewards giving up early. Define success by rules instead: all requirements traced to code and tests, existing tests unchanged and passing, and reviewer acceptance.

Problem 29: Matrix factorization on workloads and configurations

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 6, Matrix factorization.

A feedback matrix records which tuning configurations proved stable and beneficial for which workloads (1 = observed positive, blank = unobserved):

c1 c2 c3
w1 1 1
w2 1
w3 1

The learned 2-D embeddings are u_1 = (1, 0.5), u_2 = (0, 1), u_3 = (1, 0) for the workloads, and v_1 = (1, 0), v_2 = (0, 1), v_3 = (0.8, 0.4) for the configurations. TipWorked solution

What goes in the matrix. A feedback matrix records what we know about each (row, column) pair. The book weighs three sources of feedback for filling it:

  • Explicit feedback directly states an opinion. For videos that is a like or share. Here it is a validation engineer marking a configuration “pass” for a workload. It is accurate but sparse: few pairs ever get a formal validation.
  • Implicit feedback is inferred from behaviour. For videos that is clicks or watch time. Here it could be “users ran this configuration on this workload for a month without reverting it or crashing”. It is plentiful but noisy: a user may simply never have noticed the setting.
  • A combination of the two. The book chooses this, because its relevance definition already mixes explicit and implicit signals (Problem 28). Here a 1 could mean “validated as stable, or used for 30 days with no instability event”.

c1 c2 c3
w1 1.0 0.5 1.0
w2 0 1.0 0.4

Problem 30: A new GPU generation has no history

TipWorked solution

Content-based filtering recommends using features of the items and the context: the GPU’s architecture, memory type, and power limits, and the workload class.

  • Pros: it works for brand-new items, because features exist from day one, and it captures specific needs.
  • Cons: it needs domain knowledge to design features, and it rarely discovers unexpected good options.

Collaborative filtering uses only interaction history: “GPUs that behaved like yours were stable at this configuration.”

  • Pros: no feature engineering, it finds non-obvious patterns, and it is efficient.
  • Cons: the cold-start problem (no history means no recommendation) and weak coverage of niche cases.

Hybrid filtering combines the two, often sequentially. That is the book’s choice, and it fits here too.

That is far too slow for interactive tuning.

Problem 32: Ranking repair actions

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 7, Choosing the right ML category.

After a failed run, the system can choose among repair actions: re-plan with a clarified requirement, refresh the context, re-run a tool step, add a missing test, or escalate to a human. Frame “which action first?” as learning to rank. Compare pointwise, pairwise, and listwise approaches, and choose one to start with. What is tricky about the labels?

TipWorked solution

Learning to rank applies supervised learning to ordering: given a query (here, a failed run) and items (repair actions), produce the best order. The book compares three approaches.

  • Pointwise. Score each action independently, for example with the predicted probability that it repairs the run, then sort by score. It is simple, and any classifier works.
  • Pairwise. Given two actions, predict which is better. RankNet, LambdaRank, and LambdaMART are standard. It learns relative order directly.
  • Listwise. Optimize the order of the whole list at once (SoftRank, ListNet, AdaRank). It is usually the most accurate, and the hardest to implement and train.

Start pointwise, as the book does. Train a binary classifier on (failed run, action) pairs, labelled 1 if that action repaired the run within the retry budget. The inputs are trace features (the attributed failure stage from Problem 16, the error types, the step where it failed) plus action features. Sort the actions by predicted probability. With only five actions, pairwise or listwise methods gain little until there is plenty of data.

The tricky part: labels exist only for actions that were tried. If the system always tried “refresh context” first, we never learn whether “re-plan” would have worked for those runs. This is selection bias in logged data, and it connects to the exploration–exploitation trade-off from Problem 31. Two remedies:

  • sometimes try a lower-ranked action, a little exploration, so every action keeps collecting outcomes,
  • record which policy chose each action, so later analysis can correct for how actions were selected.

Answer. Frame it as learning to rank with failed runs as queries and actions as items. Start with pointwise: a classifier of P(repair succeeds) per action, sorted. Move to pairwise or listwise methods with more data. Labels exist only for actions actually tried, so keep some exploration.

Problem 34: Engineering telemetry features

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 7, Feature engineering.

Apply four ideas from the book’s event features to the stability classifier: (a) bucketing, (b) “similarity to the user’s history” features, (c) a decay factor, and (d) batch versus streaming features. Also apply the book’s tip on avoiding expensive real-time feature computation.

TipWorked solution

(a) Bucketing. The book buckets distance, time until the event, and price into ordered categories. Here, bucket hotspot temperature into ranges, such as below 70, 70 to 85, 85 to 95, and above 95 °C. Instability risk often changes sharply near thermal limits, and buckets let a simple model learn “the 95+ bucket is risky” without fitting an exact curve.

(b) Similarity to history. The book creates features like “this event’s price minus the average price of events the user registered for”. The analogue is “this candidate’s voltage offset minus the average offset this unit has been stable at”, and likewise for power limit. A configuration far beyond anything this particular unit has handled is riskier than the same configuration on a unit that has run near it for months. This captures per-unit variation in silicon quality that SKU-level features cannot.

(c) Decay factor. The book weights recent interactions more heavily. Here, weight recent telemetry and stability events above old ones. A unit’s behaviour drifts: dust builds up, thermal paste ages, and new drivers change power management. A crash last week says more than a crash a year ago.

(d) Batch vs streaming features.

  • Batch (static): SKU specifications, rated power limits, architecture, the unit’s long-run stability history. Compute these periodically and store them in a feature store: a shared database of precomputed feature values, keyed by entity (here, by SKU or unit ID). Training and serving both read from it, so they use identical feature definitions and serving does not recompute anything.
  • Streaming (dynamic): current temperature, current utilization, the active workload class. Compute these at request time from live telemetry.

Avoiding expensive real-time computation. The book’s tip: rather than computing a costly derived feature live (its example is the distance from the user to the event), pass the raw inputs and let the model learn the relationship. Here, instead of computing a thermal-headroom estimate from a physical model at request time, feed the current temperature and the SKU’s limit as two features.

Answer. (a) Bucket temperature around the thermal limits. (b) Use difference-from-this-unit’s-stable-history features to capture per-unit silicon variation. (c) Decay old telemetry and events. (d) Precompute static SKU and history features into a feature store, and compute live telemetry features at request time. Pass raw inputs instead of costly derived ones.

Problem 36: Feature crosses and a factorization machine

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 8, Feature crossing and Factorization Machines.

Stability depends on combinations: a power limit that is safe on one architecture may be risky on another for ray-tracing workloads. (a) Crossing architecture (3 values) with workload type (4 values) creates how many features? Crossing game ID (1,000 values) with SKU (50 values)? (b) A factorization machine predicts the logit

\hat y = w_0 + \sum_i w_i x_i + \sum_{i<j} \langle v_i, v_j \rangle x_i x_j.

The active features are architecture = RDNA (x = 1), workload = ray tracing (x = 1), and scaled power limit (x = 0.5). The weights are w_0 = -1, w_{\text{arch}} = 0.3, w_{\text{wl}} = 0.2, w_{\text{pl}} = 0.4. The embeddings are v_{\text{arch}} = (1, 0), v_{\text{wl}} = (0.5, 1), v_{\text{pl}} = (-1, 2). Compute \hat y and the predicted probability.

TipWorked solution

(a) Feature crossing creates one new binary feature per combination of values.

  • Architecture × workload type: 3 \times 4 = 12 crossed features.
  • Game ID × SKU: 1{,}000 \times 50 = 50{,}000 crossed features, almost all of them zero for any given example.

This shows the book’s four complaints about manual crossing. Someone has to choose which pairs to cross. Choosing well needs domain knowledge. Crossing still misses higher-order interactions. And it multiplies sparsity: most of the 50,000 crosses will have too few examples to learn a reliable weight. Logistic regression without crosses cannot model interactions at all, because its output is a sum of separate feature effects.

(b) Factorization machine. An FM learns one embedding per feature and models every pairwise interaction as a dot product of embeddings. Even a pair never seen together in training gets a sensible interaction, as long as each feature was seen with others.

Linear part:

-1 + 0.3(1) + 0.2(1) + 0.4(0.5) = -0.3.

Pairwise part:

\langle v_{\text{arch}}, v_{\text{wl}} \rangle \cdot 1 \cdot 1 = 0.5 \langle v_{\text{arch}}, v_{\text{pl}} \rangle \cdot 1 \cdot 0.5 = (-1)(0.5) = -0.5 \langle v_{\text{wl}}, v_{\text{pl}} \rangle \cdot 1 \cdot 0.5 = (1.5)(0.5) = 0.75

The pairwise sum is 0.75, so

\hat y = -0.3 + 0.75 = 0.45, \qquad p = \frac{1}{1 + e^{-0.45}} \approx 0.611.

If the label is “stable and beneficial”, the model gives this configuration about a 61% chance. Note that the interaction between workload and power limit (+0.75) contributes more than any single feature’s linear term (0.3, 0.2, and 0.2).

Answer. (a) 12 crosses for architecture × workload, and 50,000 for game × SKU, which is very sparse. (b) Linear part -0.3, pairwise part 0.75, so \hat y = 0.45 and p \approx 0.611.

Problem 37: Cross-entropy and normalized cross-entropy

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 8, Offline metrics.

A model predicts whether an agent run will be accepted at first review. On six runs, the labels are (1, 0, 0, 1, 0, 0) and the predictions are (0.8, 0.1, 0.3, 0.6, 0.2, 0.1). Compute the model’s cross-entropy (CE), the CE of a baseline that always predicts the background acceptance rate, and the normalized cross-entropy (NCE). What does the result mean?

TipWorked solution

Binary cross-entropy averages -[y \ln p + (1-y)\ln(1-p)] over examples. The book uses it as both the training loss and an offline metric. Lower is better.

Model CE. The log terms, one per run:

y p term
1 0.8 \ln 0.8 = -0.223
0 0.1 \ln 0.9 = -0.105
0 0.3 \ln 0.7 = -0.357
1 0.6 \ln 0.6 = -0.511
0 0.2 \ln 0.8 = -0.223
0 0.1 \ln 0.9 = -0.105

The terms sum to -1.525, so \text{CE}_{\text{model}} = 1.525 / 6 \approx 0.254.

Baseline CE. The background acceptance rate is 2/6 = 1/3. A model that always predicts 1/3 scores \ln(1/3) = -1.099 on each positive and \ln(2/3) = -0.405 on each negative:

\text{CE}_{\text{base}} = \frac{2(1.099) + 4(0.405)}{6} \approx 0.637.

NCE divides the model’s CE by the baseline’s:

\text{NCE} = \frac{0.254}{0.637} \approx 0.40.

Meaning. NCE below 1 means the model beats the naive “predict the average” baseline. At 0.40 it removes about 60% of the baseline’s loss. NCE of 1 or more would mean the model is no better than knowing the base rate.

Raw CE alone is hard to read, because it depends on how common positives are. NCE makes models comparable across periods whose acceptance rates differ. That matters when the agent improves and the base rate drifts upward.

Answer. Model CE ≈ 0.254, baseline CE ≈ 0.637, NCE ≈ 0.40. The model clearly beats predicting the background rate.

Problem 38: Labels that arrive late

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 8, Constructing the dataset; Serving; Other Talking Points.

A run’s true outcome (accepted, reverted, or abandoned) may take days to become known. (a) Adapt the book’s labelling rule for clicks to this setting, and discuss how to choose the time window. (b) Why should the model be trained continually, and what risk does that bring? (c) Why does calibration matter if the predicted probability decides how many retries a run gets?

TipWorked solution

(a) Labelling with a window. The book labels an impression positive if the user clicks within t seconds, and negative otherwise, with t as a hyperparameter. The analogue: a run is positive if its change is accepted within t days, and negative if it is rejected, reverted, or still open at t days.

Choosing t is a trade-off:

  • Short t: labels arrive fast, so the model stays fresh, but slow-but-successful runs get mislabelled as failures.
  • Long t: labels are more accurate, but the newest runs have no label yet, so the model lags behind the current agent version.

Look at the distribution of time-to-acceptance and pick t that covers most acceptances, such as its 90th percentile. Labels can also be corrected later if a “negative” run is accepted after t.

(b) Continual learning. The book notes that even a 5-minute delay in updating an ad model hurts performance, because user behaviour shifts quickly. Here, the agent, the codebase, and the workflow templates all change week to week, so a model trained once goes stale. A continual learning pipeline fine-tunes on fresh labelled runs, evaluates the new model, and deploys it only if the metrics improve.

The risk the book names is catastrophic forgetting: fine-tuning only on recent data erases what the model knew about older patterns. Common mitigations are to mix a replay sample of older runs into each update and to keep a fixed evaluation set that covers old cases.

(c) Calibration. A model is calibrated when its predicted 0.3 really means 30% of such runs succeed. If the retry budget depends on the predicted probability (for example, “give up below 0.2”), a model that ranks runs correctly but is overconfident will stop retrying runs that would have succeeded. The book flags calibration for ad click prediction because predicted probabilities feed into money decisions. Here they feed into compute and reviewer decisions.

Checking it. Group held-out runs into bins by predicted probability (0 to 0.1, 0.1 to 0.2, and so on). In each bin, compare the average prediction with the fraction that actually succeeded. A calibrated model gives matching numbers. Plotted, this is a reliability diagram, which should lie on the diagonal.

Fixing it after training, using a held-out set the model was not trained on:

  • Platt scaling fits a one-feature logistic regression that maps the model’s raw score s to \sigma(a s + b), learning just two numbers, a and b. It needs little data, but it can only correct an S-shaped distortion.
  • Isotonic regression fits any non-decreasing step function from score to probability. It can fix any distortion that keeps the ranking, but it needs more held-out data or it overfits.

Neither changes the order of predictions, so ranking metrics are unaffected. Only the probabilities become trustworthy. Recalibration also matters if the model was trained with class weights (Problem 7), which deliberately distort its probabilities.

Answer. (a) Label a run positive if it is accepted within t days, choosing t from the time-to-acceptance distribution (fresher labels versus more accurate ones). (b) Train continually because the agent and codebase drift, and guard against catastrophic forgetting with replay and a fixed evaluation set. (c) Calibrate, because probability thresholds decide the retry budget.

Traditional vs session-based.

  • A traditional recommender learns a user’s long-term, slowly changing interests from their whole history.
  • A session-based recommender predicts the next item from the current session, because interests are short-lived and depend on context. Someone browsing rentals in Lisbon this evening cares about Lisbon listings, whatever they booked last year.

What a step means depends on the steps around it in this run: “edit file” right after “read failing test” is a fix attempt, while “edit file” right after “read spec” is a first implementation. So model traces as sessions, where each run is a sequence of steps.

Learning step embeddings. The book learns listing embeddings the way word2vec learns word embeddings, from co-occurrence within a sliding window:

  1. Start with random embeddings for each step type. Richer vocabularies work too, such as (tool, target-file-type) pairs.
  2. Slide a window over each trace. Pull the central step’s embedding toward the steps in its window (positive pairs) and push it away from randomly sampled steps (negative pairs).

Uses for Project 19.

Problem 42: The loss on one positive and one negative pair

Inspired by Project 18 (context and intent pre-check). Book: Chapter 9, Choosing the loss function.

File embeddings for context discovery are trained from developer sessions using the book’s pairwise loss. For a positive pair (two files opened together while fixing a ticket), the embedding dot product is 2.0. For a negative pair (a central file and a random file), it is 1.5. Compute the loss on each pair using the book’s three steps, and say which pair the next update will change the most.

TipWorked solution

The book computes the loss on a pair in three steps:

  1. Similarity: the dot product of the two embeddings.
  2. Sigmoid: squash it into a probability that the pair is positive, \sigma(s) = 1 / (1 + e^{-s}).
  3. Binary cross-entropy against the label: -\ln \sigma(s) for a positive pair, and -\ln(1 - \sigma(s)) for a negative pair.

Positive pair, s = 2.0:

\sigma(2.0) = \frac{1}{1 + e^{-2}} \approx 0.881, \qquad \text{loss} = -\ln 0.881 \approx 0.127.

Negative pair, s = 1.5:

\sigma(1.5) \approx 0.818, \qquad \text{loss} = -\ln(1 - 0.818) = -\ln 0.182 \approx 1.70.

The total for the two pairs is about 1.83.

Which pair changes most. The negative pair is the problem: the model is 82% sure two unrelated files belong together. Its loss (1.70) is more than 13 times the positive pair’s (0.127). Its gradient with respect to the score is larger too: \sigma(1.5) \approx 0.818 against 1 - \sigma(2.0) \approx 0.119 in magnitude, about 7 times. The next update will mostly push these two embeddings apart.

The full loss sums such terms over all positive pairs, all negative pairs, and (with the improvements from Problem 41) the global-context pairs and hard negatives.

Answer. Positive pair: \sigma \approx 0.881, loss \approx 0.127. Negative pair: \sigma \approx 0.818, loss \approx 1.70. The negative pair dominates the update, pushing the unrelated files apart.

Problem 44: A weighted score for two configurations

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 10, Defining the ML objective.

For one workload, two candidate configurations have these predictions:

Performance gain Change in performance per watt P(instability)
A +8% −2% 0.03
B +5% +3% 0.005

Score each with S = 1.0 \cdot \text{gain} + 0.5 \cdot \Delta\text{efficiency} - 200 \cdot P(\text{instability}), with the percentages as plain numbers. Which wins? Repeat with an instability weight of -20. What does this show, and how does it compare with Problem 2’s hard constraint?

TipWorked solution

Why a weighted score at all. The book considers three ways to turn “engagement” into an ML objective for the news feed:

  1. Maximize one implicit reaction, such as clicks or dwell time. There is plenty of data, because every user produces these signals, but they are weak evidence: a click can be curiosity followed by disappointment.
  2. Maximize one explicit reaction, such as likes or shares. These state a real opinion, but few users ever give them, so the data is sparse.
  3. Maximize a weighted score over several reactions, implicit and explicit, each with a weight reflecting its business value.

The book chooses option 3 because it uses every signal and lets the business say how much each one matters. It scores a post as a weighted sum of predicted reactions: a share counts more than a like, a like more than a click, and hide or block get negative weights. The weights are business choices, and the model only supplies the probabilities.

The same three options exist here. Optimizing only the implicit, plentiful signal (performance gain, measured on every run) ignores risk. Optimizing only the explicit, rare one (no crash) ignores the point of tuning. The weighted score below is option 3.

Weight -200 on instability:

S_A = 8 + 0.5(-2) - 200(0.03) = 8 - 1 - 6 = 1.0 S_B = 5 + 0.5(3) - 200(0.005) = 5 + 1.5 - 1 = 5.5

B wins clearly. A’s extra 3% of performance does not pay for its sixfold higher crash risk.

Weight -20 on instability:

S_A = 8 - 1 - 0.6 = 6.4 S_B = 5 + 1.5 - 0.1 = 6.4

A tie. With a mild instability penalty, A’s larger performance gain catches up.

What this shows. The ranking is decided by the weights, which encode how much the business fears a crash relative to a few percent of performance. Choosing them is a product decision, as the book says about reaction weights. It should be made explicitly, with stakeholders, not left to whatever the engineer typed in.

Weighted score vs hard constraint.

  • A weighted score lets a large enough gain buy any amount of risk: a +40% configuration with P = 0.1 scores 40 - 20 = 20 at weight -200.
  • Problem 2’s constraint, P(\text{instability}) < \tau, never allows that trade.

For a safety property, the hard constraint is the more defensible default. Within the configurations that pass the constraint, a weighted score is still useful for balancing performance against efficiency. The project brief itself frames stability as a requirement to maintain, not a quantity to trade.

Answer. At weight -200: S_A = 1.0 and S_B = 5.5, so B wins. At weight -20: both score 6.4, a tie. The weights decide the winner and are a business choice. For stability, use a hard constraint first, then a weighted score among the configurations that pass it.

Problem 45: One multi-task network for performance, power, and stability

Inspired by Project 17 (GPU operating parameters from telemetry). Book: Chapter 10, Model development.

We need predictions for performance gain, power draw, and instability for every candidate configuration. Compare training three independent networks with one multi-task network. Specify the heads and the loss. Then adapt the book’s fix for “passive users”, users who rarely react, to the fact that instability events are rare.

TipWorked solution

N independent networks vs one multi-task network. The book rejects independent networks for two reasons:

  • they are expensive to train and maintain,
  • rare tasks get too little data to learn from.

Both apply here, and the second applies strongly: instability events are rare, while performance and power are measured on every run.

Multi-task design. Shared layers take the (GPU, workload, configuration) features and learn a common representation, for example “how hard is this configuration pushing this chip”. Then three heads:

Head Task type Loss
Performance gain regression Huber loss (robust to the occasional wild benchmark run)
Power draw regression Huber, or MSE
Instability binary classification binary cross-entropy, possibly class-weighted (Problem 7)

Why Huber for the regression heads. The book lists MSE, MAE, and Huber loss as regression losses. With error e = y - \hat y:

  • MSE (e^2) gives smooth gradients that shrink as the error shrinks, but squaring lets one wild benchmark run dominate. An error of 10 points contributes 100 times as much as an error of 1.
  • MAE (|e|) is robust to such outliers, but its gradient has the same size however small the error, which makes fine convergence jumpy.
  • Huber loss is quadratic for small errors and linear for large ones, with a crossover at \delta:

L_\delta(e) = \begin{cases} \tfrac12 e^2 & |e| \le \delta \\ \delta\,\big(|e| - \tfrac12\delta\big) & |e| > \delta \end{cases}

With \delta = 1, an error of 0.5 costs 0.125, the same as half-MSE. An error of 10 costs 9.5 instead of half-MSE’s 50. Benchmark runs occasionally produce wild numbers (a background update, a thermal event), so Huber keeps MSE’s smooth behaviour near the answer without letting those runs dominate.

The total loss is a weighted sum of the three task losses, L = \lambda_{\text{perf}} L_{\text{perf}} + \lambda_{\text{power}} L_{\text{power}} + \lambda_{\text{stab}} L_{\text{stab}}. The weights \lambda are hyperparameters that stop the task with the largest loss values from dominating training. Because performance and power data is plentiful, the shared layers learn good representations from it, and the rare instability head benefits. That is the book’s “training data for one task helps the others”.

Adapting the passive-user fix. In the news feed, most users rarely like or share, so every reaction head predicts near zero for them, and the model learns little about them. The book adds dense implicit tasks: dwell time (a regression head) and skip (a classification head). These carry signal on every impression, even for silent users.

The analogue: hard crashes are the “likes”, rare and decisive. Add heads for dense precursor signals that show up on most runs, such as counts of corrected errors, throttling events, or clock-stretching that telemetry may already record. These are this project’s “dwell time”. They give the stability side of the network a learning signal on every run, not only on the rare ones that crash, and they let the system flag a configuration as trending toward instability before it ever crashes.

Answer. Use one multi-task network: shared layers plus performance and power regression heads (Huber loss) and an instability classification head (weighted BCE), trained on a weighted sum of the losses. It is cheaper than three models and lets plentiful performance data help the rare stability task. Add heads for dense precursor signals, the counterpart of dwell time for passive users, so stability learning gets signal on every run.

Problem 46: Affinity, age, and evolving vocabulary

Inspired by Project 18 (context and intent pre-check). Book: Chapter 10, Feature engineering.

Adapt three groups of the book’s news feed features to predicting whether a ticket is sufficient for the agent: (a) user-author affinity, (b) the post’s age, and (c) hashtags, including the book’s tokenization, ID, and vectorization choices for them.

TipWorked solution

(a) Affinity features. The book reports that user-author affinity is among the strongest predictors of engagement. It uses features like the like rate toward an author, the length of the friendship, and close-friend status. For tickets, the useful affinity is between the ticket’s author and the code it touches:

  • the author’s past sufficiency rate: of this author’s earlier tickets on this component, the fraction the agent fixed without clarification,
  • whether the author owns or frequently commits to the referenced code, since owners tend to leave out context they take for granted,
  • how long the author has worked on the component.

The book’s “being mentioned in the post” feature becomes binary features such as “the ticket names a specific file or function” and “the ticket links a failing test”.

(b) Age. The book buckets a post’s age (under an hour, 1 to 5 hours, up to over a month) and one-hot encodes it. Ticket age matters too, and similar buckets work. An old ticket may describe code that has since changed, which is a source of conflicting information, one of the project’s gap types.

(c) Hashtags become component labels and tags. Labels like display-resume or pm/idle-states evolve as teams invent new ones. The book’s three steps:

  • Tokenization. Concatenated tags such as “lifeisgood” are split with the Viterbi algorithm, which finds the most probable segmentation into words. The same works for labels like displayresume, giving “display resume”.
  • Tokens to IDs. Use feature hashing (Problem 21), because it assigns IDs to labels never seen before.
  • Vectorization. Use a light method (TF-IDF or word2vec), not a transformer. A tag is a word or two with no sentence context to exploit, so a transformer adds cost without benefit. The book makes this same argument for hashtags.

Answer. (a) Use author-to-code affinity: the author’s past sufficiency rate, code ownership, and tenure, plus binary “names a file or test” features. (b) Bucket ticket age, since old tickets risk conflicting with changed code. (c) Segment tags with Viterbi, hash them to IDs, and vectorize with TF-IDF or word2vec rather than a transformer.

Problem 47: Traceability as a graph problem

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 11, Choosing the right ML category and Model selection.

A traceability record links requirements to plan steps, plan steps to code changes, and code changes to tests. Represent this as a graph. Give one graph-level, one node-level, and one edge-level prediction task that Project 19 needs. Then explain why a pairwise classifier on (requirement, code change) misses information that a graph neural network can use.

TipWorked solution

The graph. Nodes are requirements, plan steps, code changes, and tests, each with features (text embedding, size, type). Edges are the links “addresses”, “implements”, and “verifies”, with features of their own, such as text similarity and shared files.

The book’s three task types, here:

Level Book’s example Project 19 task
Graph is this compound an enzyme? will this whole run be accepted?
Node is this user a spammer? is this requirement dropped, with no path to a passing test? Is this step where the run went wrong?
Edge will these two users connect? does this code change implement this requirement? (recover links the agent did not record)

Why not just a pairwise classifier? The book’s first option for PYMK takes two users and predicts a connection. Its weakness is that it ignores social context: two users with four mutual connections who know each other are far likelier to connect than two users with nothing in common. The pair’s features alone cannot show that.

Here, whether change C implements requirement R depends a lot on context. If C is linked to a plan step that is linked to R, and C’s tests mention R’s acceptance criteria, the link is very likely, even if R’s text and C’s diff look dissimilar.

A graph neural network uses that context. It computes each node’s embedding by repeatedly aggregating information from its neighbours. Each node’s embedding then reflects its one-hop and multi-hop neighbourhood. The probability of an edge is a similarity of the two node embeddings, such as their dot product, exactly as in the book. GCN, GraphSAGE, and GAT are common architectures, chosen by experiment.

Answer. Build a graph of requirements, steps, changes, and tests. Graph-level: will the run be accepted. Node-level: is a requirement dropped, or is a step faulty. Edge-level: does change C implement requirement R. A pairwise classifier sees only the two endpoints, while a GNN folds in each node’s neighbourhood, which is where the strongest evidence for a missing link lies.

Problem 48: Labels from graph snapshots

Inspired by Project 19 (traceable workflows and failure feedback). Book: Chapter 11, Constructing the dataset.

At time t, a traceability graph has nodes R1, R2 (requirements), S1 (a plan step), and C1, C2 (code changes), with edges R1–S1, S1–C1, and R2–C2. By time t+1, reviewers have added the links R1–C1 and S1–C2. (a) List every candidate pair (a non-edge at t) and label it. (b) Requirement–requirement and change–change links are not allowed in this schema. How do the counts change? (c) Why are features computed from the t snapshot and not from t+1?

TipWorked solution

The book builds link prediction data in three steps: snapshot the graph at t, compute node and edge features on that snapshot, and label each candidate pair by whether an edge exists at t+1.

(a) Five nodes give \binom{5}{2} = 10 pairs. Three are already edges at t, leaving 7 candidates:

Pair Edge at t+1? Label
R1–R2 no 0
R1–C1 yes 1
R1–C2 no 0
R2–S1 no 0
R2–C1 no 0
S1–C2 yes 1
C1–C2 no 0

That is 2 positives and 5 negatives.

(b) Remove the type-invalid pairs R1–R2 and C1–C2. That leaves 5 candidates: 2 positives and 3 negatives.

Filtering by schema is free and removes negatives that teach nothing: the model never needs to learn that requirements don’t link to requirements. This is a small instance of the book’s candidate-narrowing idea (Problem 49). In real graphs, negatives vastly outnumber positives, so imbalance handling from Problem 7 applies too.

(c) Everything the model sees must come from before the outcome it predicts. Computing features on the t+1 graph would let the new links leak into the inputs. For example, an “S1 and C2 share a neighbour” feature would only be true because of the very edge we are predicting. That is data leakage, and it makes offline scores look better than real use, where the future graph is unknown. For evaluation, apply the same rule one step later: features from t+1, labels from t+2.

Answer. (a) 7 candidates: R1–C1 and S1–C2 are positive, and R1–R2, R1–C2, R2–S1, R2–C1, and C1–C2 are negative. (b) Dropping type-invalid pairs leaves 5: 2 positive and 3 negative. (c) Features come from the t snapshot so that the links being predicted cannot leak into the inputs.

Problem 49: Narrowing candidates and precomputing

Inspired by Project 18 (context and intent pre-check). Book: Chapter 11, Serving.

A monorepo has 2,000,000 files, and each file imports about 30 others on average. (a) Following the book’s friends-of-friends idea, how many 2-hop candidates does a file have at most, and how large is the reduction? (b) The organization has 50,000 repositories, and 20% receive tickets on a given day. If related-context lists are precomputed for every repository daily, what fraction of that work is wasted? (c) Should related context be precomputed (batch) or computed on demand (online), and how often should it be refreshed?

TipWorked solution

(a) Friends of friends. The book observes that most new connections form between friends of friends. With 1,000 friends each, a user has about 1{,}000^2 = 10^6 friends of friends, which shrinks the search from 1 billion users to about a million.

The analogue is the dependency graph: relevant context usually sits within two import hops.

30 \times 30 = 900 \text{ two-hop candidates at most}

(Fewer in practice, because neighbourhoods overlap.)

\frac{2{,}000{,}000}{900} \approx 2{,}200 \text{ times smaller}.

The model then scores 900 files instead of 2 million.

(b) Batch waste. Daily precomputation for all 50,000 repositories, when only 20% (10,000) are used, wastes

\frac{40{,}000}{50{,}000} = 80\% \text{ of the work}.

The book raises the same issue: precomputing for every user wastes compute on users who never log in that day.

(c) Batch or online? The book picks batch for People You May Know for two reasons. Computing on the fly for 300 million daily users is too slow, and the social graph changes slowly, so precomputed lists stay valid for days. It refreshes weekly, and more often for new users, whose networks grow fast.

The same reasoning fits here, with the book’s own optimizations:

  • Precompute only for active repositories. That removes most of the waste from (b).
  • Refresh on change rather than on a fixed clock. A dependency graph changes when code merges, so recompute a repository’s lists after merges that touch imports. Fast-moving repositories refresh more often, the counterpart of new users.
  • Fall back to an on-demand computation for a repository with no precomputed list. The book’s prediction pipeline does the same when a user’s list is missing.

Answer. (a) At most 900 two-hop candidates, about 2,200 times fewer than 2 million. (b) 80% of daily precomputation is wasted. (c) Batch-precompute for active repositories, refresh after import-changing merges (more often for fast-moving repositories), and compute on demand when no list exists.

Problem 50: Feedback loops in the context ranker

Inspired by Project 18 (context and intent pre-check). Book: Chapter 11, Other Talking Points (with positional bias from Chapters 2, 9, and 10).

After a few months, the context ranker keeps suggesting the same popular files, the agent mostly uses whatever is listed first, some suggestions are ignored again and again, and many outcomes are not known for days. Name the bias or problem behind each symptom, explain the feedback loop, and give a mitigation for each.

TipWorked solution

1. Rich-get-richer (representation bias). The book warns that frequent users dominate People You May Know training data, so they get recommended more, make more connections, and become even more represented.

Here, files that are suggested more get opened more, generate more positive labels, and get suggested still more. Niche but crucial files, such as a rarely touched configuration header, starve.

Mitigation: monitor how concentrated suggestions are; down-weight very frequent files during training; keep some exploration slots in the list (Problem 31).

2. Positional bias. Items at the top of a list get used more because they are at the top, whatever their relevance. The book raises this for image search, similar listings, and the news feed.

The agent’s habit of using the first item makes the labels say “position 1 was relevant” even when it was not.

Mitigation: add the item’s position as a training feature, then set it to a fixed value at serving time; or occasionally shuffle the top few items to measure how much position alone matters. (Inverse-propensity weighting is the more formal version of this correction, beyond the book’s scope.)

3. Repeatedly ignored suggestions. The book suggests ranking a recommendation lower each time a user ignores it.

Mitigation: add a feature counting how many times this file was suggested for similar tickets and not used, so the ranker learns to demote it. Also, since the pre-check’s job includes conflict detection, a file that is suggested but never used may be stale, and that is worth flagging.

4. Delayed feedback. The book asks when an unaccepted recommendation should count as negative, since people may act days later.

Mitigation: use the time-window labelling from Problem 38. Count a suggestion as negative only after the ticket’s fix is merged without using it. Correct labels that change later.

All four are feedback loops: the system’s own output shapes the data it learns from next. That is why monitoring (Problem 11) watches input and output distributions, not just accuracy.

Answer. Rich-get-richer bias: monitor concentration, down-weight frequent files, and explore. Positional bias: train with position as a feature and probe it with small shuffles. Ignored suggestions: count ignores as a feature to demote them. Delayed feedback: label within a time window after the fix merges.
